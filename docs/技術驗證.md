## 與 `docs/架構.md`、`CLAUDE.md` 假設不符的地方（作者已決定，2026-11-12）

|---|---|---|---|
| D1 | 功能規格 C1：畫質用 `height<=N` | 直式影片會選錯：N=720 拿到 360x640（見第 5 項） | 改用 `-S res:N`，官方文件說明它以短邊計算，直式也正確 |

檔案大小：

| 情況 | 出現什麼 |
|---|---|
| 單一格式、`protocol` 是 `https` | 確切值 `filesize` |

## 3. 下載 MP3 的進度

結論：階段依序是「下載聲音 → ExtractAudio（轉檔）→ EmbedThumbnail（嵌入封面）→ MoveFiles」。轉檔沒有進度數字。

```
yt-dlp.exe <共用參數> -f ba/b -x --audio-format mp3 --embed-thumbnail
  -o "%(title)s [%(id)s].%(ext)s" --windows-filenames --no-playlist
  --print "after_move:FILE %(filepath)s"
  --progress --newline
  --progress-template "download:DL %(info.{id,format_id})j %(progress.{status,downloaded_bytes,total_bytes,total_bytes_estimate,fragment_index,fragment_count,speed,eta,elapsed})j"
  --progress-template "postprocess:PP %(info.{id})j %(progress.{status,postprocessor})j"
  -P "<TEMP>\mp3\中文 資料夾" https://www.youtube.com/watch?v=FtSUD4KDscE
```


（每行開頭的數字是程序啟動後的秒數。）

要點：

- **加了 `--print` 會進入安靜模式，下載進度整個不見**，要再加 `--progress` 才會輸出。第一次跑就踩到。
- 啟動後前幾秒（查資訊）沒有任何輸出，「查詢中」這個狀態要由後端自己在啟動時設定。
- 下載階段有 `downloaded_bytes` 和 `total_bytes`，可以直接算百分比，不必解析文字（解決 U3 的 a）。
- 後處理只有 `started`／`finished`，沒有百分比。1 小時的音訊轉 MP3 要好幾秒到幾十秒，這段只能顯示階段名稱。
- 進度字典的完整鍵還有 `filename`、`tmpfilename`、`_percent`、`_default_template` 等；`total_bytes_estimate`、`fragment_index`、`fragment_count` 在這些 https 格式上沒有出現。
- 成品用 ffprobe 檢查：`mp3` 音訊一軌，加上 `png` 1280x720 的封面（`attached_pic=1`）。

## 4. 下載 MP4 的進度

結論：影像、聲音各下載一次，用 `info.format_id` 分辨；之後是「Merger（合併）→ MoveFiles」。合併沒有進度數字。

```
yt-dlp.exe <共用參數> -S res:1080,vcodec:h264,acodec:m4a --merge-output-format mp4 <同第 3 項的檔名與進度參數> ...watch?v=FtSUD4KDscE
```


要點：

- 第一個檔是影像（`137`）、第二個是聲音（`140`），每個檔的 `downloaded_bytes` 都從頭算起。
- 總進度的算法：先從第 1 項的資訊拿到兩個格式的 `filesize` 當分母，下載時把「已完成的檔 + 目前這個檔的 `downloaded_bytes`」當分子（解決 U3 的 b）。
- 合併只有開始／結束，這支影片花 0.08 秒；4K 那支 0.17 秒。合併通常很快，轉檔才慢。
- 成品：1080p 那支是 `h264` + `aac`；2160p 那支是 `vp9` + `aac`（見 D2）。

## 5. 畫質選擇

結論：`height<=N` 對直式影片會選錯，`-S res:N` 三種影片都正確。

```
yt-dlp.exe <共用參數> -f "bv*[height<=720]+ba/b[height<=720]" --no-playlist --print "%(format_id)s %(width)sx%(height)s %(vcodec).4s+%(acodec).4s %(ext)s" <網址>
yt-dlp.exe <共用參數> -S res:720 ...
yt-dlp.exe <共用參數> -S res:720,vcodec:h264,acodec:m4a ...
```

| 影片 | N | `-f height<=N` | `-S res:N` | `-S res:N,vcodec:h264,acodec:m4a` |
|---|---|---|---|---|
| 16:9（ZH，最高 1080p） | 360 | 640x360 vp9+opus webm | 640x360 vp9+opus webm | 640x360 avc1+mp4a mp4 |
| | 720 | 1280x720 avc1+opus mkv | 1280x720 avc1+opus mkv | 1280x720 avc1+mp4a mp4 |
| | 1080 | 1920x1080 avc1+opus mkv | 同左 | 1920x1080 avc1+mp4a mp4 |
| | 2160 | 1920x1080（沒有更高的，拿最高） | 同左 | 1920x1080 avc1+mp4a mp4 |
| 4:3（ZOO，最高 240p） | 360–2160 | 320x240 av01+opus webm | 同左 | 320x240 avc1+mp4a mp4 |
| 直式（SHORT，1080x1920） | 360 | **144x256** | 360x640 | 360x640 avc1+mp4a mp4 |
| | 720 | **360x640** | 720x1280 | 720x1280 avc1+mp4a mp4 |
| | 1080 | **608x1080** | 1080x1920 | 1080x1920 avc1+mp4a mp4 |
| | 2160 | 1080x1920 | 1080x1920 | 1080x1920 avc1+mp4a mp4 |
| 4K（UHD） | 720 | 1280x720 av01+opus webm | 同左 | 1280x720 avc1+mp4a mp4 |
| | 1080 | 1920x1080 av01+opus webm | 同左 | 1920x1080 avc1+mp4a mp4 |
| | 2160 | 3840x2160 av01+opus webm | 同左 | 3840x2160 **vp9**+mp4a（預設容器 mkv） |

要點：

- 非 16:9 的橫式影片兩種寫法都對；舊版掉到 360p 的問題（C1）兩種寫法都不會發生。
- 直式影片的 `height` 是長邊，所以 `height<=720` 只挑得到 360x640（D1）。
- 最後一欄是沒加 `--merge-output-format mp4` 時 yt-dlp 自己選的容器。加了之後 4K 的 VP9 + AAC 也能合併成 mp4（第 4 項實際下載過）。
- 影片沒有 N 那麼高時，三種寫法都會拿到現有的最高畫質，不會失敗。

## 6. 取消

結論：一定要結束整棵程序樹。只結束 `Popen` 拿到的那個程序，內層的 yt-dlp 和 FFmpeg 會繼續跑。

`yt-dlp.exe` 啟動後是兩個程序（外層啟動器、內層真正的程式），FFmpeg 是內層的子程序：

```
before: yt-dlp.exe(pid 126368 <- 98628), yt-dlp.exe(pid 84160 <- 126368), ffmpeg.exe(pid 125356 <- 84160)
```

| 時機 | 做法 | 結果 |
|---|---|---|
| 下載中 | `Popen.kill()` | 外層立刻結束（`wait()` 回傳 1），**內層 5 秒後還在** |
| 下載中 | `taskkill /PID <pid> /T /F` | 0.41 秒後全部結束，檔案不再變動 |
| FFmpeg 轉檔中 | `Popen.kill()` | **內層和 `ffmpeg.exe` 都還在，mp3 繼續變大**（4 秒內從 2.6 MB 長到 12.6 MB） |
| FFmpeg 轉檔中 | `taskkill /PID <pid> /T /F` | 0.43 秒後全部結束，檔案不再變動 |

## 8. Deno

結論：Deno 和 `yt-dlp.exe` 放同一個資料夾就會被自動找到；要指定路徑時必須用絕對路徑。目前沒有 Deno 也查得到資訊，但官方已標示為棄用。

```
yt-dlp.exe --ignore-config -v [--js-runtimes ...] --print "%(format_id)s %(height)s" https://www.youtube.com/watch?v=jNQXAC9IVRw
```

| 設定 | `[debug] JS runtimes:` | 結果 |
|---|---|---|
| 不給參數，`deno.exe` 與 `yt-dlp.exe` 同資料夾，PATH 上沒有 deno | `deno-2.9.8` | 用 `<專案>\bin\deno.EXE` |
| `--js-runtimes deno:bin/deno.exe`（相對路徑） | `none` | **找不到**，也不會退回同資料夾或 PATH |
| `--js-runtimes deno:<專案>\bin\deno.exe`（絕對路徑） | `deno-2.9.8` | 用指定的那一份 |
| `--js-runtimes deno:<專案>\bin`（資料夾） | `deno-2.9.8` | 用該資料夾裡的 deno |
| `--no-js-runtimes` | `none (disabled)` | 不用任何執行環境 |

```
[debug] JS runtimes: deno-2.9.8
[youtube] [jsc:deno] Solving JS challenges using deno
[debug] [youtube] [jsc:deno] Running deno: '<專案>\bin\deno.exe' run --ext=js --no-code-cache --no-prompt --no-remote --no-lock --node-modules-dir=none --no-config --no-npm --cached-only -
```

有無 Deno 的差別（`-J`）：

| 影片 | 有 Deno | 沒有（`--no-js-runtimes`） |
|---|---|---|
| ZOO | 3.8 秒，25 個格式 | 2.8 秒，24 個格式，1 個警告 |
| ZH | 4.0 秒，20 個格式 | 3.0 秒，19 個格式，1 個警告 |
| SHORT | 3.8 秒，47 個格式 | 2.7 秒，46 個格式，1 個警告 |
| UHD | 4.3 秒，52 個格式 | 3.0 秒，51 個格式，1 個警告 |

沒有 Deno 時的警告：

```
WARNING: [youtube] No supported JavaScript runtime could be found. Only deno is enabled by default; ... YouTube extraction without a JS runtime has been deprecated, and some formats may be missing.
```

要點：

- 這四支影片少掉的都是同一個格式（`18`，360p 的影音合一檔），最高畫質沒有少。但官方明講這個做法已棄用，之後可能直接失敗，所以還是要附 Deno。
- 有 Deno 每次查詢多約 1 秒。
- 要確保用的是 App 附的那一份：一律傳 `--js-runtimes deno:<絕對路徑>`。指定路徑後不會退回 PATH 上的 deno（相對路徑那次的結果可以佐證）。
- yt-dlp 執行 deno 時帶了 `--no-remote --no-npm --cached-only`，不會讓它連網路。

## 9. 自我更新

結論：`-U` 需要 `yt-dlp.exe` 所在的資料夾可寫入；沒有權限時結束代碼是 100，原本的版本不受影響。下載進行中也能更新。

驗證方式：把 `yt-dlp.exe` 複製到暫存資料夾，在那裡測，不動 `bin/` 裡的那一份。

已經是最新版：

```

    Latest version: stable@2026.10.26 from yt-dlp/yt-dlp
    yt-dlp is up to date (stable@2026.10.26 from yt-dlp/yt-dlp)
```

實際換版（先降到 2026.10.21 再升回來）：

```
$ yt-dlp --update-to 2026.10.21   -> exit=0  5.9s
    Current version: stable@2026.10.26 from yt-dlp/yt-dlp
    Requested version: stable@2026.10.21 from yt-dlp/yt-dlp
    Current Build Hash: f5389d3698ecde4ef06f4e6b1ce0294fe9ac1396228c8990b8d3416d6d177a7d
    Updating to stable@2026.10.21 from yt-dlp/yt-dlp ...
    Updated yt-dlp to stable@2026.10.21 from yt-dlp/yt-dlp
  files: yt-dlp.exe (17,880,111), yt-dlp.exe.old (23,575,744)
```

同一個 `yt-dlp.exe` 正在下載時更新：

```
  download still running: True
$ yt-dlp -U   -> exit=0  19.1s
    Updating to stable@2026.10.26 from yt-dlp/yt-dlp ...
    Updated yt-dlp to stable@2026.10.26 from yt-dlp/yt-dlp
$ yt-dlp --version   -> 2026.10.26
  files: yt-dlp.exe (23,575,744), yt-dlp.exe.old (17,880,111)
  download still running after the update: True
```

資料夾不可寫入（用 `icacls` 對暫存資料夾加上「拒絕寫入、新增、刪除子項目」，模擬 `C:\Program Files`，測完已移除）：

```
$ yt-dlp -U   -> exit=100  4.1s
    Updating to stable@2026.10.26 from yt-dlp/yt-dlp ...
    ERROR: Insufficient permissions to write to <TEMP>\update-locked\yt-dlp.exe.new
$ yt-dlp --version   -> 2026.10.21
  files: yt-dlp.exe (17,880,111)
```

要點：

- 更新的做法是：下載成 `yt-dlp.exe.new`，把目前的改名成 `yt-dlp.exe.old`，再把新的換上去。所以需要在同一個資料夾建立、改名、刪除檔案的權限。
- 更新後會留下 `yt-dlp.exe.old`（上面兩次都留著），所以資料夾會多佔一份的空間。原始碼裡下次更新開始時會先刪它；這次沒有單獨驗證刪除的時機。
- 更新成功的結束代碼是 0，權限不足是 100，訊息是 `Insufficient permissions to write to <路徑>`。
- 版本資訊從 `api.github.com` 查，未登入有每小時次數上限，App 不應該每次啟動都查。
- 這次的模擬只擋了資料夾的寫入權限，沒有在真正的 `C:\Program Files` 底下測（需要系統管理員權限）。

### 對「外部程式放哪裡」的建議（待作者確認後寫成決策紀錄 0005）

建議採架構文件的第一個選項：**安裝檔採「僅目前使用者」安裝，裝到 `%LOCALAPPDATA%\Programs\`，外部程式跟 App 放在一起**。

| | 僅目前使用者安裝（建議） | 首次啟動時複製到 `%LOCALAPPDATA%\media-downloader\bin` |
|---|---|---|
| `-U` 能不能成功 | 可以，資料夾本來就可寫入 | 可以 |
| 佔用空間 | 一份 | 兩份（安裝資料夾一份、複製出去一份），不含 ffprobe 也多約 278 MiB |
| 安裝時要不要系統管理員權限 | 不用 | 裝到 `Program Files` 就要 |
| 程式複雜度 | `binaries/` 只要回傳安裝資料夾 | 要處理複製、兩份版本不一致、App 更新後要不要覆蓋 |
| 缺點 | 只裝給目前的使用者；重新安裝或升級 App 時，安裝檔附的 yt-dlp 可能比使用者已更新的還舊 | 解除安裝後 `%LOCALAPPDATA%` 會留下一份 |

兩個選項都要處理「安裝檔不要把比較新的 yt-dlp 蓋回舊的」，這是打包階段的事。

## 12. 同時下載

結論：三個下載各開一個程序、各有自己的輸出管線，進度不會混在一起。

```
三個執行緒各自執行第 3 項的 MP3 指令（ZOO、ZH、UHD），輸出到同一個資料夾
```

```
## three downloads at once: 10.6s
  2PuFyjAs7JA: exit=0 progress lines=10 lines about another video=0
  jNQXAC9IVRw: exit=0 progress lines=15 lines about another video=0
  FtSUD4KDscE: exit=0 progress lines=16 lines about another video=0
     1,284,313  4K 2K 1080p 720p 480p video resolution test [2PuFyjAs7JA].mp3
```

要點：

- 每一行進度都帶 `info.id`，三條管線裡都沒有出現別支影片的 ID。
- 三個同時跑 10.6 秒，跟單獨跑一個（約 9 秒）差不多，時間大多花在各自查資訊。

### 同時 4、5 個（2026-11-15，階段 3e）

結論：4、5 個沒有被限速，也沒有 429；作者決定把範圍從 1–3 放寬到 1–5，預設維持 3。零星的 HTTP 403 在 3 個時就會發生，跟放寬無關。

做法：`scripts/manual/stage3e.py concurrency`，經過 `build()` 的整組服務，同樣五支 5–15 分鐘的影片，共 104 次下載。

MP3 320（每輪 5 支，4 輪）：

| 同時幾個 | 5 支下載完的時間 | 失敗 | 429 | 自動重試 |
|---|---|---|---|---|
| 1 | 72–76 秒 | 0／20 | 0 | 0 |
| 3 | 20–25 秒 | 1／20 | 0 | 0 |
| 4 | 16–22 秒 | 1／20 | 0 | 0 |
| 5 | 10–11 秒 | 2／20 | 0 | 0 |

MP4 480p（每輪同時跑 N 支，2 輪）：

| 同時幾個 | 合計速度 | 每支平均速度 | 失敗 |
|---|---|---|---|
| 3 | 5.7、8.7 MB/s | 約 3.3 MB/s | 1／6 |
| 4 | 12.3、9.5 MB/s | 約 3.0–3.4 MB/s | 1／8 |
| 5 | 14.5、10.1 MB/s | 約 2.8–3.3 MB/s | 1／10 |

- 每支的速度不隨數量下降，合計速度跟著數量增加：沒有被限速。
- 7 次失敗全部是 `ERROR: unable to download video data: HTTP Error 403: Forbidden`，發生在資料開始傳之前，分散在四支不同的影片，同一支下一輪就成功。目前歸成 `unknown`（可以重試）。
- 403 的比例：3 個時 2／26、4 個時 2／28、5 個時 3／30；一次 1 個時 0／20。樣本小，分不出 3、4、5 的差別，也不能斷定 1 個時不會發生。
- 要不要由後端自動再試一次，留到階段 4 規劃時決定。

- 指定 `--ffmpeg-location` 之後，yt-dlp 只看那個資料夾，不會去用 PATH 上別的 FFmpeg（這台電腦的 PATH 上另有一份，`exe versions` 那行沒有列出 ffprobe）。
- 這個 FFmpeg 是 GPL 的完整靜態建置，功能遠超過我們需要的（轉 MP3、嵌入封面、合併）。換成較小的建置也許能再省很多，這次沒有測。
- 這個 FFmpeg 建置是 GPL 授權，關於頁與 README 要照 GPL 的要求標示（App 本身維持 MIT，分開的執行檔）。

## 14. 檔名重複（實驗 A）

結論：「整個下載在任務自己的資料夾完成，最後由我們搬到下載資料夾」可行。成品檔名在開始傳資料前約 5 秒就拿得到，「略過」可以在一個位元組都沒下載時停下來。yt-dlp 自己的略過機制不適合用。

**下載前能不能知道檔名**：`-J` 的結果裡沒有檔名。但下載指令加 `--print "before_dl:NAME %(filename)s"`，會在開始傳資料前印出來：

```
yt-dlp.exe <共用參數> -f ba/b -x --audio-format mp3 --embed-thumbnail -o "%(title)s.%(ext)s" --windows-filenames --no-playlist
  --print "before_dl:NAME %(filename)s" --print "after_move:FILE %(filepath)s" <進度參數> -P <資料夾> <ZH>
```

```
   4.26 NAME <TEMP>\before\公視新創電影《最後的詩句》30秒搶先看！.webm
   9.31 DL {"id": "FtSUD4KDscE", "format_id": "251"} {"status": "downloading", "downloaded_bytes": 1024, ...}
  10.04 FILE <TEMP>\before\公視新創電影《最後的詩句》30秒搶先看！.mp3
```

- MP3 這時的副檔名是原始檔的（`.webm`），成品檔名要自己換成 `.mp3`；MP4（有 `--merge-output-format mp4`）直接就是 `.mp4`。
- `NAME` 比第一筆進度早約 5 秒（MP3 4.26 → 9.31，MP4 4.13 → 9.19）。收到 `NAME` 就結束程序樹：結束代碼 1，資料夾是空的。

**yt-dlp 自己的略過**（同一個資料夾連跑兩次，有沒有加 `--no-overwrites` 結果一樣）：

```
[info] Writing video thumbnail 37 to: <TEMP>\skip\.tmp\Me at the zoo.webp
[download] <TEMP>\skip\Me at the zoo.mp3 has already been downloaded
[ExtractAudio] Not converting audio <TEMP>\skip\Me at the zoo.mp3; file is already in target format mp3
[ThumbnailsConvertor] Converting thumbnail "<TEMP>\skip\.tmp\Me at the zoo.webp" to png
[EmbedThumbnail] ffmpeg: Adding thumbnail to "<TEMP>\skip\Me at the zoo.mp3"
```

| | MP3 | MP4 |
|---|---|---|
| 認得出成品已存在 | 是（它知道轉檔後的副檔名） | 是 |
| 第二次花多久 | 5.3–5.8 秒 | 4.5 秒 |
| 有沒有碰原本的檔案 | **有**：重新下載縮圖，對使用者原本的 mp3 再跑一次嵌入封面（檔案的修改時間沒變） | 沒有 |
| 結束代碼 | 0，跟真的下載完分不出來，要另外解析那一行文字 | 同左 |

不適合的原因：會動到使用者原本的檔案；只有「略過」，沒有「自動改名」；而且成品要是都在任務自己的資料夾完成，yt-dlp 根本看不到下載資料夾裡有什麼。

**建議的做法**：

1. yt-dlp 只認得任務自己的資料夾（`-P <下載資料夾>\<任務的暫存資料夾>`），下載、轉檔、合併都在裡面。
2. 收到 `NAME`：算出成品檔名（換副檔名）。設定是「略過」而且下載資料夾已有同名檔案 → 結束程序樹、刪掉暫存資料夾、回報「已略過」。
3. 收到 `FILE`（成品完成）：搬到下載資料夾。暫存資料夾在下載資料夾底下，同一顆磁碟，搬動只是改名，不必複製。
   - 覆蓋：`os.replace`。
   - 自動改名：`os.rename` 在 Windows 上目標已存在時會失敗，失敗就換下一個名字（`歌名 (1).mp3`、`歌名 (2).mp3`…）。兩個任務同時搬同名的檔也不會互相蓋掉。
   - 略過：平常在第 2 步就停了；如果下載期間才冒出同名檔案，這裡再擋一次（成品丟掉，回報已略過）。

`DownloadRequest` 與 `DownloadResult` 建議的改法（還沒改，等作者同意）：

| 型別 | 改動 | 說明 |
|---|---|---|
| 新增 `OnDuplicate`（`domain/`） | `skip`、`overwrite`、`rename` | 值跟約定 2.10 的 `onDuplicate` 一樣 |
| `DownloadRequest` | 加 `on_duplicate: OnDuplicate` | 由佇列在開始下載時從設定帶入 |
| `DownloadResult` | 加 `skipped: bool = False` | `True` 時 `file_path` 是原本就在那裡的檔案（「開啟資料夾」要用）、`size_bytes` 是它的大小 |

不需要新的事件：略過是 `download()` 的回傳值，服務層收到後呼叫 `DownloadTask.skip()`（`downloading → done`，轉換表已經有這一條）。

已知的代價：

- 「略過」要等 yt-dlp 啟動約 4 秒才知道檔名，這段顯示「下載中 0%」，然後變成「已略過」。
- 檔名只用標題：不同影片但標題相同，會被當成重複（略過時不下載、覆蓋時蓋掉）。
- 轉換表的 `queued → done（略過）`在這個做法下用不到（輪到之前不知道檔名）。建議先留著不動。

## 15. 標題含特殊字元時的檔名

結論：`--windows-filenames` 把不允許的字元換成長得像的全形字，不是底線。太長的標題會讓下載失敗，要加 `--trim-filenames`。

做法：用 `--replace-in-metadata title "^.*$" <假標題>` 換掉標題（真的影片很難剛好找到這些字元），`-o "%(title)s.%(ext)s" --windows-filenames`。

| 標題 | 檔名（不含副檔名） |
|---|---|
| `a\b/c:d*e?f"g<h>i\|j` | `a⧹b⧸c：d＊e？f＂g＜h＞i｜j` |
| `AC/DC - Back: "Live" <1080p>?` | `AC⧸DC - Back： ＂Live＂ ＜1080p＞？` |
| `trailing dot.` | `trailing dot.`（成品是 `trailing dot..mp3`） |
| `trailing space `（結尾空格） | 原樣保留（成品是 `trailing space .mp3`） |
| `...` | `...` |
| `CON` | `CON`（**沒有處理**保留名稱） |
| `🎵 歌名 🎵` | 原樣保留 |
| 300 個中文字 | 原樣保留，**實際下載失敗**（結束代碼 1，錯誤訊息是那個過長的路徑） |

- 第一個標題實際下載 MP3 成功，磁碟上的檔名與 `after_move` 印出的一致。
- 引擎要做的：加 `--trim-filenames`（長度在實作時實測決定）；搬到下載資料夾前確認結果仍在下載資料夾內（CLAUDE.md 的安全規則）。`CON.mp3` 這類保留名稱留給搬檔那一步處理。

## 16. 結束程序樹：`taskkill /T /F` 與 Job Object（實驗 B）

結論：建議用 Job Object。只有它能在 App 被強制結束時把下載一起帶走；取消也比較快，而且不必另外啟動一個程式。

做法：每個任務建立一個 Job Object，設定「最後一個控制代碼關閉時結束裡面所有程序」（`JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`）。yt-dlp 以暫停狀態啟動（`CREATE_SUSPENDED`），放進 Job 之後才讓它開始跑，所以它再啟動的內層程序、Deno、FFmpeg 一定都在 Job 裡。控制代碼只有 App 持有：App 不管怎麼結束，Windows 都會關掉它，Job 裡的程序跟著結束。

**App 被強制結束**（另一個 Python 程序扮演 App，啟動下載後被 `taskkill /F` 結束，不帶 `/T`，等於工作管理員的「結束工作」）：

| App 被結束的時機 | 沒有 Job Object | 有 Job Object |
|---|---|---|
| 下載中 | 1 秒內全部結束（yt-dlp 印下一行進度時發現管線斷了，自己結束） | 1 秒內全部結束 |
| FFmpeg 轉檔中 | **1 秒後、5 秒後 `yt-dlp.exe` 兩個和 `ffmpeg.exe` 都還在，mp3 繼續變大**；20 秒後才不見（轉完之後 yt-dlp 要印東西才發現管線斷了） | 1 秒內全部結束，檔案不再變動 |

```
## app force-killed during ffmpeg, children started with: plain
  after 5 s: yt-dlp.exe(pid 26388 <- 34776), yt-dlp.exe(pid 11984 <- 26388), ffmpeg.exe(pid 41780 <- 11984)
    files still growing: ['.tmp\\White Noise 1 Hour Long.mp3']
## app force-killed during ffmpeg, children started with: job
  after 1 s: none
    files still growing: none
```

沒有 Job Object 時，留在背景的時間取決於轉檔要多久（這次是 1 小時的音訊，約十幾秒）。兩種做法都會留下暫存資料夾，要靠下次啟動時清理。

**取消**：

| 時機 | `taskkill /PID <pid> /T /F` | `TerminateJobObject` |
|---|---|---|
| 下載中 | 0.29 秒後 `wait()` 返回，程序全部結束 | 0.004 秒 |
| FFmpeg 轉檔中 | 0.33 秒 | 0.005 秒 |
| 之後刪暫存資料夾 | 第一次就成功 | 第一次就成功 |

比較：

| | `taskkill /T /F` | Job Object |
|---|---|---|
| App 被強制結束時 | 轉檔中的程序留在背景 | 全部結束 |
| 取消 | 要多啟動一個程式（也要隱藏視窗）；輸出是系統語系的編碼 | 一個系統呼叫 |
| 取消時剛好有新的子程序啟動 | 可能漏掉（先列出程序樹再逐一結束） | 不會漏 |
| 程式碼 | 幾行 | 約 40 行 `ctypes`（結構定義與四個系統呼叫） |
| 代價 | — | 讓暫停的程序開始跑用的是 `NtResumeProcess`，微軟沒有正式寫進文件（psutil 的 `resume()` 也是用它）。不想用的話可以不暫停、啟動後立刻放進 Job，理論上有極短的空窗 |

沒測到的：App 本身已經在別的 Job 裡（Windows 8 以上支援巢狀 Job，應該沒問題）；打包後的 App。

## 17. MP3 封面裁成正方形（實驗 C）

結論：做得到，在 yt-dlp 的指令上多加兩個參數。成品的封面是置中裁切的正方形 JPEG。

```
--embed-thumbnail --convert-thumbnails jpg
--ppa "ThumbnailsConvertor+ffmpeg_o:-vf \"crop='min(iw,ih)':'min(iw,ih)'\""
```

（上面是 `--ppa` 的值在參數清單裡的樣子：一個字串，內含雙引號與單引號。yt-dlp 會像 shell 一樣把它拆開，雙引號用來保住單引號；單引號是給 FFmpeg 看的，沒有的話逗號會被當成濾鏡的分隔，錯誤是 `No such filter: 'ih):min(iw'`。第一次就踩到。）

yt-dlp 實際執行的 FFmpeg 指令：

```
ffmpeg -y -loglevel repeat+info -f image2 -pattern_type none -i file:wide.webp -update 1 -bsf:v mjpeg2jpeg -movflags +faststart -vf "crop='min(iw,ih)':'min(iw,ih)'" file:wide.jpg
ffmpeg -y -loglevel repeat+info -i file:wide.mp3 -i file:wide.jpg -c copy -map 0:0 -map 1:0 -write_id3v1 1 -id3v2_version 3 -metadata:s:v "title=Album cover" -metadata:s:v "comment=Cover (front)" -movflags +faststart file:wide.temp.mp3
```

用 ffprobe 檢查成品：

| 影片 | 不裁（對照） | 裁正方形 |
|---|---|---|
| 16:9（ZH） | `png` 1280x720，檔案 1,070,716 位元組 | `mjpeg` 720x720，443,593 位元組 |
| 直式（SHORT） | — | `mjpeg` 720x720 |
| 4:3（ZOO） | — | `mjpeg` 360x360 |

- 三個成品都是 ID3v2.3（檔頭 `ID3\x03\x00`），封面標成「Cover (front)」，是播放器普遍支援的寫法。
- 把封面取出來看過（ZH）：畫面中間的正方形，沒有變形。
- 封面改成 JPEG 之後檔案小很多（這支少了 627 KB）。
- 作者已在自己的播放器裡看過（2026-11-15）：三個樣本都看得到封面，是正方形、沒有黑邊或變形，裁掉的範圍可以接受。

## 19. 自動重試時的輸出

結論：重試那一行印在 **stdout**，不是 stderr；括號裡的次數會重新從 1 算，不能直接當成「第幾次重試」。

連線被切斷一次、之後恢復（預設參數）：

```
DL {"id": "LXb3EKWsInQ", "format_id": "701"} {"status": "downloading", "downloaded_bytes": 261120, "total_bytes": 966132483, ...}
[download] Got error: ("Connection broken: ConnectionResetError(10054, '遠端主機已強制關閉一個現存的連線。', None, 10054, None)", ConnectionResetError(...)). Retrying (1/10)...
[download] Destination: <TEMP>\retry\out\COSTA RICA IN 4K 60fps HDR (ULTRA HD) [LXb3EKWsInQ].f701.mp4
DL {"id": "LXb3EKWsInQ", "format_id": "701"} {"status": "downloading", "downloaded_bytes": 262144, "total_bytes": 966132483, "elapsed": 0.061}
```

連線一直不通（`--retries 3 --socket-timeout 10`）：

```
stdout  +0.0s: [download] Got error: (...). Retrying (1/3)...
stdout  +2.0s: [download] Got error: ('Unable to connect to proxy', NewConnectionError(...)). Retrying (2/3)...
stdout  +4.1s: ... Retrying (3/3)...
stdout  +8.1s: ... Retrying (1/3)...
stdout +10.1s: ... Retrying (2/3)...
stdout +12.1s: ... Retrying (3/3)...
stderr: ERROR: 
stderr: [download] Got error: ('Unable to connect to proxy', NewConnectionError(...)). Giving up after 3 retries
（stderr 這兩行印了兩次；結束代碼 1，斷線後 14.6 秒結束）
```

要點：

- 辨認重試：stdout 以 `[download] Got error:` 開頭、以 `Retrying (N/M)...` 結尾的行。
- 次數走完一輪會再來一輪（上面是 1、2、3、1、2、3），所以 `ConnectionLost.attempt` 由引擎自己數，不用括號裡的數字。
- 重試成功後接著下載，`downloaded_bytes` 從斷掉的地方繼續，不會歸零。
- 最後的失敗訊息：**`ERROR:` 那一行是空的，內容在下一行**。錯誤分類要看整段 stderr，不能只看 `ERROR:` 開頭的那一行。
- 訊息裡作業系統的文字是中文（跟第 7 項一樣），只能比對 `Got error`、`Retrying`、`Giving up after` 這些英文部分。
- 這裡的斷線還是用 proxy 模擬的，而且「連不上 proxy」是立刻被拒絕；真的斷網時每次嘗試可能要等到逾時，總時間會更長。真的斷網留到實作重試參數時請作者配合測。

|---|---|---|
| `watch?v=…&list=…` | 單支影片（`_type=video`） | 3.8 秒 |

- 失敗時 stdout 是 `null`，不是空的。

## 21. 播放列表裡無法下載的項目

結論：私人影片在 `--flat-playlist` 的結果裡還在，但沒有標題、時長、頻道。`available` 可以用「有沒有標題」判斷。

```
{"title": null, "duration": null, "view_count": null, "timestamp": null, "live_status": null, "availability": null,
 "channel_url": null, "uploader_url": null, "creators": null, "ie_key": "Youtube", "id": "au1PyhcecWg",
 "_type": "url", "url": "https://www.youtube.com/watch?v=au1PyhcecWg"}
```

- 在三個列表裡看到 10 個這樣的項目；抽三個單獨查，都是 `Private video`。
- 跟正常項目比：`title`、`duration` 是 `null`，`channel`、`channel_id`、`uploader`、`uploader_id` 這四個鍵**整個不存在**；`availability` 也是 `null`，不能用它判斷。
- 它仍然有 `thumbnails`（四個尺寸，是 YouTube 的替代圖）。建議無法下載的項目不給 `thumb`。
- stderr 有一行 `WARNING: [youtube:tab] YouTube said: INFO - 7 unavailable videos are hidden`，但項目其實都列出來了（42 個裡有 7 個沒有標題）。
- 有標題但沒有時長的項目也存在（1719 個裡有 7 個，沒有逐一查，推測是直播或首播），這種算可以下載、時長不知道。
- 約定 2.4 的表不用改欄位；「無法下載的項目實際長什麼樣子還沒看過」那句可以拿掉。
- 沒遇到標成「已刪除」的項目，推測長得一樣，沒驗證。

## 23. 斷線時多久回報失敗（引擎用的參數）

結論：查資訊最慢約 12 秒回報；下載中斷線，35 秒內恢復可以自己接上，真的斷了 45–110 秒回報失敗。

模擬兩種斷線（`scripts/spike/s12_timeouts.py`，本機 proxy）：「拒絕連線」是每次嘗試立刻失敗；「沒有回應」是連得上但對方永遠不回，每次嘗試都要等到逾時。

查資訊：

| 參數 | 沒有回應 |
|---|---|
| `--socket-timeout 5 --extractor-retries 1` | 22.0 秒 |
| `--socket-timeout 5 --extractor-retries 0`（採用） | 11.6 秒 |

- 查一支影片要發兩個請求，每個等 5 秒逾時；`--extractor-retries 1` 會各再試一次。
- 拒絕連線的情況（第 7 項的做法）約 10 秒。
- 代價：YouTube 偶爾回傳不完整的資料時，yt-dlp 不會自己再試，要使用者按重試。
- 另外有 60 秒的硬性上限防止程序卡住（1719 支的播放列表要 11 秒，不能設太短）。

下載中：

| 參數 | 拒絕連線 | 沒有回應 |
|---|---|---|
| 預設（`--retries 10`，第 7 項） | 43.4 秒 | 沒測 |
| `--socket-timeout 10 --retries 5 --fragment-retries 5` | 22.7 秒 | 120.6 秒 |
| `--socket-timeout 10 --retries 3 --fragment-retries 3 --retry-sleep 5 --retry-sleep fragment:5`（採用） | 44.6 秒 | 110.6 秒 |

採用那一組的重試時間點（斷線後的秒數）：

```
拒絕連線：0.0、7.0、14.1、23.1、30.1、37.2，44.6 秒放棄
沒有回應：10.0、25.0、40.0、65.1、80.1、95.1，110.6 秒放棄
```

- yt-dlp 會把重試次數走兩輪，所以 `--retries 3` 實際是 6 次。
- 加 `--retry-sleep 5` 的原因：拒絕連線時每次嘗試只花 2 秒，不等的話 15 秒就放棄，Wi-Fi 短暫斷一下就失敗。
- 每次重試引擎都送一個 `ConnectionLost`，次數從 1 遞增；資料恢復後歸零。
- 以上都是模擬。

真的關 Wi-Fi（作者實測，2026-11-14，用 `scripts/manual/engine.py`）：

| 測試 | 結果 |
|---|---|
| 沒網路時查資訊 | 1.6 秒回 `network`。訊息是名稱解析失敗：`Failed to resolve 'www.youtube.com' ([Errno 11001] getaddrinfo failed)` |
| 下載中關 Wi-Fi，第 3 次重試後開回來 | 斷線約 10 秒後第 1 次 `ConnectionLost`，之後每 5 秒一次（共 3 次）；恢復後從斷掉的位元組接著下載到完成，沒有殘留程序 |
| 下載中關 Wi-Fi，不開回來 | `ConnectionLost` 第 1 到 6 次（斷線後約 10、15、20、25、30、35 秒），斷線後約 40 秒回 `network`；暫存資料夾已刪除 |

- 真的斷網是名稱解析立刻失敗，比模擬的兩種都快：每次嘗試幾乎不花時間，間隔就是 `--retry-sleep` 的 5 秒。
- 第一次要等 10 秒，是進行中的連線等到 `--socket-timeout` 才發現斷了。
- 所以實際的行為是：斷線 35 秒內恢復可以自己接上，超過約 40 秒回報失敗。參數維持不變。
- 真實的訊息已加進測試樣本（`errors/offline_*_real.txt`），原本的比對規則就涵蓋（`Failed to resolve`、`getaddrinfo failed`、`Giving up after`）。

## 還沒驗證的項目
