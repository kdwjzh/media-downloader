## 摘要

- 階段 3 拆成五段（3a–3e），每段各自可以驗收，一段一個工作階段。
- 先寫「介面與後端的約定」，把階段 2 的樣張需要的資料形狀定下來，後端照著做，階段 4 才接得上。
- 領域層的狀態與錯誤代碼改用階段 2 定案的名稱（9 種狀態、11 個錯誤代碼）。
- 全程不開介面：每段都用測試驗收，另外各有一支手動腳本可以對真的 YouTube 跑一次。
- 這個階段結束時，舊版問題清單裡屬於後端的項目要逐項驗過。

## 4. 每段要注意的事

### 3a

- 約定是這個階段最重要的產出：階段 4 的橋接層和 `frontend/src/api/` 都照它寫。
- 事件要能讓介面只靠事件就畫出整個佇列，不必另外輪詢。
- 「預覽還在查詢中時又貼了新網址」的做法表示：佇列要能接受只有網址、還沒有資訊的項目（狀態 `fetching`）。

### 3b

- `CLAUDE.md`「呼叫 yt-dlp 的坑」那幾條全部適用。
- 測試用的輸出樣本從 `scripts/spike/` 再錄一次存成檔案，個人路徑先遮掉。
- 結束程序樹的做法在這段定案：`taskkill /T /F`，或 Windows Job Object。Job Object 可以順便解決「App 被強制結束時下載程序留在背景」，建議優先評估，結論寫成決策紀錄。
- `retrying` 狀態來自 yt-dlp 輸出的重試訊息，要確認那一行的格式並錄樣本。
- 重試次數與逾時要調整，技術驗證量到預設值下最久 43 秒才判定失敗。

### 3c

- 進度事件要節流，不要每收到一行就送一次。
- MP4 總進度的分母來自查資訊時兩個格式的大小；拿不到大小時要有退路。
- 檔名取自標題，要處理 Windows 不允許的字元（技術驗證沒測到這項）。

### 3d

- 設定檔或資料庫壞掉時不能讓 App 打不開：退回預設值並把壞檔改名留存。
- 歷史紀錄每筆有自己的編號（舊版問題 C10）。
- App 新版檢查用 GitHub 的發佈資訊，repo 還是私人時查不到，要能正常顯示「沒有新版」。

## 5. 階段 3 結束時要驗過的清單

舊版問題中屬於後端的：

| # | 問題 | 驗法 |
|---|---|---|
| U3 | 進度條不跟著百分比跑 | MP3、MP4 各下載一次，記錄事件序列：百分比只增不減，MP4 不會跑兩次 |
| C1 | 畫質選錯 | 一般、直式、4K 影片各測一次 |
| C3 | 取消無效 | 下載中、轉檔中各取消一次：程序全部結束、暫存資料夾刪除 |
| C4 | 一次只能下載一個 | 同時 3 個 |
| C5 | 設定不會存檔 | 重新啟動後設定還在 |
| C6 | yt-dlp 不會更新 | 更新指令成功與失敗各一次 |
| C9 | 網址判斷 | `music.youtube.com`、`m.youtube.com`、`youtu.be`、Shorts |
| C10 | 歷史紀錄刪錯筆 | 同一支影片下載兩種格式，刪其中一筆 |
| C11 | 只用 print | 失敗的下載在記錄檔裡找得到原始錯誤訊息 |

技術驗證留下、在這個階段補驗的：

- 標題含 Windows 不允許字元時的檔名
- 播放列表中含私人或已刪除影片的項目長什麼樣子
- 超過 200 支的播放列表
- App 被強制結束時，下載程序會不會留在背景
- 真的斷網（關 Wi-Fi）時的錯誤訊息
- 同時下載 4、5 個（先問作者）

留到階段 4 決定的：關閉視窗時如果還有下載在進行，要不要先問使用者（後端的做法已定：關閉就全部停止並清掉暫存）。

留到後面階段的：會員限定影片的訊息樣本、英文系統、打包後的主控台視窗、`C:\Program Files` 下的更新。
