## 摘要

- 指令 28 個（介面叫後端做事），事件 7 種（後端主動通知介面）。`confirm_close` 與 `closeRequested` 是階段 4a 加的（關閉前確認）；`start_app_update`、`cancel_app_update`、`install_app_update` 與 `appUpdateChanged` 是階段 5b 加的（App 的一鍵更新，`decisions/0019`）。
- 佇列的畫面只靠事件就畫得出來；介面只在啟動時拿一次目前的佇列，之後不必再問。
- 進度事件每個任務最多每 0.5 秒送一次；狀態改變的事件不等，立刻送。
- 錯誤只用第 2.1 節的 13 個代碼。後端不回傳給人看的文字。
- 檔案路徑不交給介面。介面用編號叫後端「開啟資料夾」。唯一例外是設定頁要顯示的下載資料夾。
- `types.ts` 已照第 5 節改成跟約定逐欄對得上（階段 4a 補齊），由測試檢查兩邊一致。

## 1. 共通規則

### 1.1 指令怎麼來回

介面呼叫一個指令，後端做完後回覆。回覆只有兩種樣子：

| 情況 | 回覆 | 說明 |
|---|---|---|
| 成功 | `{ "ok": true, "data": … }` | `data` 的內容每個指令不同；沒有東西要回時不帶 `data` |
| 失敗 | `{ "ok": false, "error": "network" }` | `error` 是第 2.1 節 13 個錯誤代碼之一 |

- 指令名稱用小寫加底線（`add_to_queue`），是後端 Python 方法的名字。`frontend/src/api/` 把每個指令包成一個函式，其他元件不直接碰指令名稱。
- 欄位名稱用小駝峰（`durationSec`），跟 `types.ts` 現在的寫法一樣。
- 後端自己出錯（程式的 bug、收到不合規定的參數）時回 `unknown`，原因寫進記錄檔。

### 1.2 沒有值的欄位

**沒有值的欄位整個不出現**，不會出現 `null`。例如還沒查到標題的項目，資料裡就沒有 `title` 這個欄位。
這跟 `types.ts` 現在用 `?` 的寫法一致。下面的表格用「一定有」和「可能沒有」標示。

### 1.3 「來不及」的指令不算錯誤

使用者按「取消」的瞬間，那個項目可能剛好下載完。這種「任務已經不在可以做這件事的狀態」或「編號已經不存在」的情況，
後端什麼都不做，回覆成功。介面不必處理，因為畫面會跟著事件更新成正確的樣子。

每個指令的「不會有動作的情況」都列在該指令底下。

### 1.4 編號

任務編號（`QueueItem.id`）和歷史紀錄編號（`HistoryEntry.id`）都是字串，由後端產生。介面只拿來比對和傳回後端，不解讀內容。
兩種編號互不相干：同一支影片下載兩次會有兩個任務編號、兩筆歷史紀錄編號（解決舊版 C10）。

### 1.5 關閉 App

關閉時後端結束所有下載、刪掉暫存資料夾，佇列不保留。下次啟動時 `get_queue` 回傳空的清單。
所以資料形狀裡沒有任何「上次沒下載完」的欄位。

## 2. 資料形狀

### 2.1 共用的值

**Format（格式）**：`"mp3"` 或 `"mp4"`。

**quality（音質或畫質）**：一個數字，意思跟著格式走。

| 格式 | 數字的意思 | 可以用的值 |
|---|---|---|
| `mp3` | 位元率，單位 kbps | 128、192、320 |
| `mp4` | 畫質上限（短邊的像素數）。影片沒那麼高時拿現有最高的 | 144、240、360、480、720、1080、1440、2160 |

**TaskStatus（任務狀態）**：9 種，後端與介面用同一組字串。

| 值 | 意思 |
|---|---|
| `fetching` | 還不知道這支影片的資訊，正在查 |
| `queued` | 已有資訊，等待空位 |
| `downloading` | 下載中 |
| `retrying` | 連線中斷，yt-dlp 正在自動重試 |
| `converting` | 轉成 MP3 中（含嵌入封面） |
| `merging` | 合併成 MP4 中 |
| `done` | 完成（含「檔案已存在，已略過」） |
| `failed` | 失敗 |
| `cancelled` | 已取消 |

合法的狀態轉換見第 6 節。

**ErrorCode（錯誤代碼）**：13 個，後端與介面用同一組字串，也是語言檔 `error.*` 的鍵名。

| 值 | 意思 | 可以重試 |
|---|---|---|
| `invalidUrl` | 不是有效的網址 | 否 |
| `unsupportedSite` | 不支援的網站 | 否 |
| `notFound` | 影片不存在或已移除 | 否 |
| `private` | 私人影片 | 否 |
| `ageRestricted` | 年齡限制 | 否 |
| `membersOnly` | 會員限定 | 否 |
| `geoBlocked` | 地區限制 | 否 |
| `playlistNotFound` | 播放列表不存在 | 否 |
| `liveNotSupported` | 直播或即將直播 | 否 |
| `playlistUrl` | 只給網址加入佇列的項目，查出來是播放列表（見 3.2 `add_to_queue`）。只會出現在佇列項目上 | 否 |
| `network` | 網路問題 | 是 |
| `unknown` | 分類不出來的錯誤，原文在記錄檔 | 是 |
| `checksumMismatch` | 下載的 App 安裝檔跟發佈的檢查碼對不上（含檢查碼檔看不懂、下載不完整）。只會出現在 App 更新（2.15） | 是 |

### 2.7 QueueItem（佇列裡的一個項目）

| 欄位 | 型別 | 有沒有值 | 說明 |
|---|---|---|---|
| `id` | 字串 | 一定有 | 任務編號 |
| `url` | 字串 | 一定有 | |
| `format` | Format | 一定有 | |
| `quality` | 數字 | 一定有 | 加入時選的音質或畫質（G3） |
| `status` | TaskStatus | 一定有 | |
| `title` | 字串 | 可能沒有 | `fetching` 時沒有；查詢階段就失敗或被取消的也沒有。沒有時介面顯示網址 |
| `thumb` | 字串 | 可能沒有 | 縮圖網址。`fetching` 時沒有；來源沒提供時也沒有 |
| `percent` | 整數 0–100 | 見下表 | 整個任務的下載百分比。同一次下載中只增不減。MP4 的影像與聲音合成一個數字 |
| `doneBytes` | 數字 | 見下表 | 已下載的位元組（MP4 是兩個檔加起來） |
| `totalBytes` | 數字 | 見下表 | 總共要下載的位元組（MP4 是兩個檔加起來） |
| `speedBps` | 數字 | 見下表 | 速度（位元組／秒） |
| `etaSec` | 數字 | 見下表 | 預估剩餘秒數 |
| `attempt` | 數字 | 只有 `retrying` | 第幾次重試，從 1 開始 |
| `sizeBytes` | 數字 | 只有 `done` 且沒有略過 | 成品的實際檔案大小 |
| `skipped` | 布林 | 只有 `done` 且被略過時是 `true` | 檔名重複、設定是「略過」，所以沒有下載。介面顯示「檔案已存在，已略過」。其他情況這個欄位不出現 |
| `error` | ErrorCode | 只有 `failed` | 失敗的原因 |

沒有成品路徑（G3）。要開啟資料夾用 `open_task_folder` 帶任務編號。

進度欄位在每個狀態下有沒有值：

| 狀態 | `percent` | `doneBytes` | `totalBytes` | `speedBps` | `etaSec` |
|---|---|---|---|---|---|
| `downloading` | 通常有 | 有 | 通常有 | 通常有 | 通常有 |
| `retrying` | 維持中斷時的值 | 維持 | 維持 | 沒有 | 沒有 |
| 其他 7 種 | 沒有 | 沒有 | 沒有 | 沒有 | 沒有 |

`downloading` 時「通常有」的欄位，什麼情況沒有：

| 欄位 | 沒有的情況 |
|---|---|
| `percent` | 完全拿不到檔案大小（連估計值都沒有）。介面改用不確定進度條 |
| `totalBytes` | 有任何一個檔的大小不知道。介面省略「/ 總大小」。這時 `percent` 可能還是有（見下面的算法） |
| `speedBps` | 剛開始下載、還算不出速度 |
| `etaSec` | 沒有 `totalBytes` 或沒有 `speedBps` |

`percent` 的算法（實作與測試在領域層）：

1. 每個檔的大小都知道：`percent` = 所有檔已下載的位元組 ÷ 所有檔的總位元組。MP4 就是「影像已下載 + 聲音已下載」÷「影像大小 + 聲音大小」。
2. 有檔的大小不知道（例如聲音還沒開始下載、事先也沒查到）：每個檔各佔一樣的比例。MP4 的影像跑 0–50%、聲音跑 50–100%。
3. 正在下載的那個檔連自己的大小都不知道：沒有 `percent`。
4. 不管哪一種，算出來比上次小就維持上次的值。
5. 重試或重新加入後是新的一次下載，從 0 重新開始。
6. 剛開始下載、yt-dlp 還沒送出第一筆進度的那幾秒，`percent` 是 0。

### 2.15 AppUpdateStatus（App 更新到哪裡）

| 欄位 | 型別 | 有沒有值 | 說明 |
|---|---|---|---|
| `stage` | `"idle"`、`"downloading"`、`"verifying"`、`"ready"`、`"installing"`、`"failed"` | 一定有 | 見下表 |
| `receivedBytes` | 整數 | 可能沒有 | 只有 `downloading` 有：已下載的位元組 |
| `totalBytes` | 整數 | 可能沒有 | `downloading` 且伺服器有給大小時才有 |
| `error` | `network`、`unknown`、`checksumMismatch` | 可能沒有 | 只有 `failed` 有 |

| `stage` | 意思 | 下一步 |
|---|---|---|
| `idle` | 沒有在更新（含取消之後） | `start_app_update` |
| `downloading` | 先抓檢查碼檔，再下載安裝檔 | 完成 → `verifying`；`cancel_app_update` → `idle` |
| `verifying` | 核對 SHA-256 | 一致 → `ready`；不一致 → `failed`（`checksumMismatch`） |
| `ready` | 安裝檔核對過，等介面叫 `install_app_update` | 介面在還有下載沒完成時先問使用者 |
| `installing` | 安裝程式已經啟動，App 隨即關閉 | — |
| `failed` | 失敗，下載的檔案已刪掉 | `start_app_update`（重試） |

## 3. 指令

### 3.1 查詢

#### `lookup`：查詢網址

查一個網址是什麼：單支影片就回傳預覽資料，播放列表就回傳清單。大約要等 3–4 秒。

| | |
|---|---|
| 參數 | `url`（字串）：使用者貼的內容，原樣傳入 |
| 回傳 | LookupResult |
| 可能的錯誤 | 除了 `playlistUrl` 以外的 11 個都有可能。`playlistNotFound` 只會出現在播放列表網址；`liveNotSupported` 是查到直播或即將直播 |

- 網址同時帶影片和播放列表（`watch?v=…&list=…`）時，當成單支影片。
- 頻道網址（例如 `/@某頻道/videos`）當成播放列表，項目是那個頻道的影片。
- 第一版只接受 YouTube 的網域，其他網站回 `unsupportedSite`；不是 http(s) 網址、或 `watch` 網址沒有影片編號，回 `invalidUrl`。
- 已結束、沒有留存檔的直播回 `notFound`。
- 後端會記住查過的結果（到 App 關閉為止）。之後 `add_to_queue` 只要給網址，後端就知道標題和縮圖。
- 沒有「取消查詢」的指令。使用者關掉查詢中的預覽時，介面丟掉晚到的結果就好。

### 3.2 佇列

#### `add_to_queue`：加入佇列

把一個或多個網址加進佇列，全部用同一組格式與音質／畫質。加入後自動開始，超過同時下載數的排隊。

| | |
|---|---|
| 參數 | `urls`（字串的清單，至少一個）、`format`（Format）、`quality`（數字） |
| 回傳 | `{ taskIds }`：新任務的編號，順序跟 `urls` 一樣 |
| 可能的錯誤 | `invalidUrl`：有任何一個不是 http(s) 網址，這時一個都不加入。`unknown`：`format` 或 `quality` 不是 2.1 列的值 |

三種用法都是這一個指令：

| 用法 | `urls` | 新任務的狀態 |
|---|---|---|
| 預覽查到了，按「加入佇列」 | 那一個網址 | `queued`，已有標題和縮圖 |
| 預覽還在查，使用者又貼了新網址 | 還在查的那個網址 | `fetching`，只有網址；後端查到後補上標題和縮圖，變成 `queued` |
| 播放列表勾選後整批加入 | 勾選的每個項目的 `url` | `queued`，已有標題和小縮圖 |

- 新任務加在佇列最下面，順序跟 `urls` 一樣。介面會收到 `tasksChanged` 事件。
- 這個指令會把 `format` 和 `quality` 記成「上次用的」（寫進設定），介面會收到 `settingsChanged` 事件。
- 同一個網址可以重複加入，每次都是新的任務。
- 網址會先照 `lookup` 的規則整理（去掉前後空白、補 `https://`）再檢查。
- 只給網址的任務查出來是播放列表時，任務變成 `failed`，錯誤是 `playlistUrl`，不會自動展開。使用者要重新貼上，等清單出現後勾選。
- 下載資料夾與同時下載數在加入時不檢查；檔名重複的規則在任務開始下載的那一刻讀設定。

## 4. 事件

後端主動送給介面的通知。每個事件是一個物件，用 `type` 分辨是哪一種。
`frontend/src/api/` 提供一個訂閱函式，其他元件透過它收事件。事件實際怎麼從 Python 送到網頁見 `decisions/0012`（後端呼叫網頁掛在 `window` 上的函式）。

同一個任務的事件一定照發生的順序送到。

| `type` | 一句話 | 什麼時候送 |
|---|---|---|
| `tasksChanged` | 這些任務是新的，或內容變了 | 加入佇列、狀態改變、查到標題與縮圖 |
| `tasksRemoved` | 這些任務從佇列拿掉了 | `remove_task`、`clear_finished` |
| `taskProgress` | 這個任務下載到哪裡了 | 下載中，每個任務最多每 0.5 秒一次 |
| `historyAdded` | 多了一筆歷史紀錄 | 任務下載完成（被略過的不算） |
| `settingsChanged` | 設定變了 | `update_settings`、`choose_download_folder`、`add_to_queue` 記住上次用的格式 |
| `appUpdateChanged` | App 更新到了哪一步 | `start_app_update` 之後的每一步；下載中最多每 0.5 秒一次 |
| `closeRequested` | 使用者按了關閉視窗，但還有任務沒結束 | 按下關閉時；視窗沒有關 |

### `tasksChanged`：任務新增或改變

告訴介面一個或多個任務現在的完整樣子。

| 欄位 | 型別 | 說明 |
|---|---|---|
| `type` | `"tasksChanged"` | |
| `tasks` | QueueItem 的清單 | 每個都是完整的項目，不是只有改變的欄位 |

介面的做法：編號已經在佇列裡的，整個換掉，位置不動；編號沒看過的，照清單順序加到佇列最下面。
這個事件不節流：狀態一改變就送。
網頁忙著處理上一個事件時，排在後面、連在一起的幾個 `tasksChanged` 會合成一個送：同一個任務只出現一次，是最新的樣子，位置照它第一次出現的。照上面的做法套用，結果跟一個一個收到一樣；中間經過的狀態可能看不到（2026-11-17，4c）。

### `tasksRemoved`：任務被移除

| 欄位 | 型別 | 說明 |
|---|---|---|
| `type` | `"tasksRemoved"` | |
| `ids` | 字串的清單 | 被拿掉的任務編號 |

### `taskProgress`：下載進度

| 欄位 | 型別 | 說明 |
|---|---|---|
| `type` | `"taskProgress"` | |
| `progress` | TaskProgress | 見 2.8 |

多久送一次：

- 只有 `downloading` 狀態會送。
- 每個任務**最多每 0.5 秒一次**。yt-dlp 一秒會輸出很多行進度，後端只留最新的一筆。同時下載 5 個時，介面每秒最多收到 10 個進度事件。
- 數字沒變就不送。
- 狀態一改變（例如下載完進入轉檔），後端立刻送 `tasksChanged`，還沒送出的進度直接丟掉。所以介面不會在轉檔開始後才收到舊的百分比。

### `historyAdded`：多了一筆歷史紀錄

| 欄位 | 型別 | 說明 |
|---|---|---|
| `type` | `"historyAdded"` | |
| `entry` | HistoryEntry | 新的那一筆。介面如果正開著歷史紀錄畫面，把它加到最上面 |

刪除和清空是介面自己叫的指令，指令成功後介面自己更新畫面，所以沒有對應的事件。

### `settingsChanged`：設定變了

| 欄位 | 型別 | 說明 |
|---|---|---|
| `type` | `"settingsChanged"` | |
| `settings` | Settings | 完整的設定 |

### `appUpdateChanged`：App 更新到了哪一步

| 欄位 | 型別 | 說明 |
|---|---|---|
| `type` | `"appUpdateChanged"` | |
| `status` | AppUpdateStatus | 見 2.15 |

下載進度跟任務的進度一樣：最多每 0.5 秒一次，太早到的丟掉。取消之後，被取消的那一輪不會再送任何事件。介面收到 `ready` 時：佇列沒有沒完成的項目就直接叫 `install_app_update`，有就先問。

### `closeRequested`：使用者想關閉視窗，但還有任務沒結束

| 欄位 | 型別 | 說明 |
|---|---|---|
| `type` | `"closeRequested"` | |

- 「還沒結束」是指佇列裡有任何項目不是 `done`、`failed`、`cancelled`。全部結束（或佇列是空的）時，按關閉直接關，不送這個事件。
- 視窗這時還開著。介面問使用者；要關就叫 `confirm_close`，不關就什麼都不做。
- 沒有元件在聽這個事件時，`frontend/src/api/` 直接叫 `confirm_close`（也就是照常關閉）。
- 事件送不進網頁時（頁面壞掉），後端自己直接關，不會讓視窗關不掉。

### 沒有做成事件的

| 事 | 為什麼不用事件 |
|---|---|
| 查詢網址的結果 | `lookup` 指令等到查完才回覆 |
| App 有新版 | 介面啟動時叫 `check_app_update`，後端不主動檢查 |
| yt-dlp 啟動時的自動更新 | 只寫記錄檔；設定頁讀版本時會等它做完 |
| yt-dlp 更新的結果 | `update_engine` 指令等到做完才回覆 |

## 6. 狀態轉換表

下載任務的狀態只能照這張表改變。表上沒有的轉換，領域層會丟出錯誤。

| 從 | 到 | 什麼時候 |
|---|---|---|
| `fetching` | `queued` | 查到影片資訊 |
| `fetching` | `failed` | 查詢失敗 |
| `fetching` | `cancelled` | 使用者取消 |
| `queued` | `downloading` | 有空位，輪到它 |
| `queued` | `cancelled` | 使用者取消 |
| `downloading` | `retrying` | 連線中斷，yt-dlp 自動重試 |
| `downloading` | `converting` | 下載完，開始轉 MP3（只有 MP3） |
| `downloading` | `merging` | 兩個檔都下載完，開始合併（只有 MP4） |
| `downloading` | `done` | MP4 只有一個檔、不必合併；或下載時才發現檔案已存在而略過 |
| `downloading` | `failed` | 下載失敗 |
| `downloading` | `cancelled` | 使用者取消 |
| `retrying` | `downloading` | 連線恢復 |
| `retrying` | `done` | 引擎回報下載成功，但沒有先回報連線恢復。檔案已經在資料夾裡，所以一定算完成 |
| `retrying` | `failed` | 重試次數用完 |
| `retrying` | `cancelled` | 使用者取消 |
| `converting` | `done` | 轉檔完成；或搬檔時才發現檔案已存在而略過（同一支影片加了兩次） |
| `converting` | `failed` | 轉檔失敗 |
| `converting` | `cancelled` | 使用者取消 |
| `merging` | `done` | 合併完成；或搬檔時才發現檔案已存在而略過 |
| `merging` | `failed` | 合併失敗 |
| `merging` | `cancelled` | 使用者取消 |
| `failed` | `queued` 或 `fetching` | 重試。只有錯誤是 `network` 或 `unknown` 才可以。已有影片資訊的回 `queued`，沒有的回 `fetching` |
| `cancelled` | `queued` 或 `fetching` | 重新加入。規則同上 |

- `done` 之後不能再變。
- 從佇列移除不是狀態轉換；只有 `done`、`failed`、`cancelled` 的任務可以移除。
- 一個狀態不能轉換到自己。重試中又收到「第 2 次重試」只是更新次數，狀態沒有變。
- 實作在 `backend/app/domain/task.py` 的 `TRANSITIONS`，這張表與它不一致時要一起改；`backend/tests/test_task.py` 會檢查每個合法與不合法的轉換。

```
fetching ──→ queued ──→ downloading ⇄ retrying
                              │
                              ├──→ converting ──┐
                              ├──→ merging ─────┼──→ done
                              └─────────────────┘
retrying ──→ done（引擎回報成功時，不管當下是哪個下載中的狀態都算完成）

done 以外的每個狀態 ──→ cancelled ──→ queued / fetching（重新加入）
fetching、downloading、retrying、converting、merging ──→ failed ──→ queued / fetching（重試）
```

## 7. 作者已決定的事（2026-11-14）

九題全部採用「決定」欄的做法。背景見 `decisions/0007`。

| # | 問題 | 決定 | 沒採用的做法與差別 |
|---|---|---|---|
| Q1 | `fetching` 這個狀態代表什麼？ | 只代表「還不知道影片資訊，正在查」。只有「只給網址」加入的任務會經過它；它一加入就開始查，不佔同時下載數。從預覽或播放列表加入的任務直接是 `queued`。任務輪到之後 yt-dlp 還要 3–4 秒才開始傳資料，這段顯示「下載中 0%」 | 每個任務輪到時都先經過 `fetching` 再到 `downloading`。好處是那 3–4 秒顯示的是「正在查詢影片資訊…」而不是 0%；壞處是只有網址的項目在前面有 3 個下載時，會一直顯示網址和「等待中」，輪到它才看得到標題，跟主畫面規範寫的不一樣 |
| Q2 | `watch?v=…&list=…`（從播放列表裡點開的影片）這種網址，算單支還是播放列表？ | 算單支影片。只有 `playlist?list=…` 這種純播放列表網址才展開清單 | 算播放列表：想抓一首歌的人會突然看到一整張清單 |
| Q3 | 重試、重新加入之後，項目留在原位還是移到最下面？ | 留在原位，編號不變 | 移到最下面：符合「新項目在最下面」，但列會在畫面上跳走 |
| Q4 | 按「開啟資料夾」時檔案已經被搬走或刪掉怎麼辦？ | 改開它原本所在的資料夾；連資料夾都不在就不開，回傳 `opened: "none"`。介面這時要顯示一句話，文案階段 4 再定 | 加第 12 個錯誤代碼（例如 `fileMissing`）。沒加，因為那 11 個都是「下載為什麼失敗」，這個性質不同 |
| Q5 | 使用者關掉還在查詢中的預覽時，後端要不要真的中止那次查詢？ | 不中止。讓它在背景跑完（通常 3–4 秒），介面丟掉結果。少一個指令，也少一種要測的情況 | 加 `cancel_lookup` 指令，馬上結束那個程序。只省下幾秒的背景工作 |
| Q6 | 歷史紀錄的本機縮圖怎麼交給介面？ | 直接把圖片內容放進 `thumb`（`data:image/jpeg;base64,…`），介面當一般圖片網址用，不必知道檔案在哪。每張約 10 KB；歷史紀錄到幾百筆時 `list_history` 會回傳幾 MB，到時候變慢再改成分批載入 | 由後端開一個本機網址提供圖片：資料量小，但橋接層要多做一個提供檔案的機制，而且要確認開發模式和打包後都行得通 |
| Q7 | 設定的預設值？ | 下載資料夾：使用者的「下載」資料夾；格式 MP3；MP3 音質 320 kbps；MP4 畫質最高 1080p；檔名重複時自動改名；同時下載數 3；語言跟隨系統 | 下載資料夾可以改成「音樂」資料夾，因為主要是抓音樂 |
| Q8 | 對「已經不在那個狀態的任務」下指令（例如取消一個剛好完成的項目），算成功還是錯誤？ | 算成功，什麼都不做（1.3）。所以指令的錯誤只用原本的 11 個代碼，不必另外加一組 | 另外定一組指令用的錯誤代碼（找不到任務、現在不能做這件事…）。介面要多處理幾種實際上只會在「按太快」時發生的情況 |
| Q9 | 「記住上次用的格式與畫質」由誰記？ | 後端在 `add_to_queue` 時記，然後用 `settingsChanged` 通知介面。歷史紀錄的「重新下載」不算 | 介面自己在加入佇列時另外叫一次 `update_settings`。少一種事件，但三個加入的入口（預覽、自動加入、播放列表）都要記得叫 |

- 關閉視窗時還有下載在進行，要不要先問使用者（階段 4）。
- 很大的播放列表（實測 1719 支要 11 秒、資料 2.3 MB）在介面上怎麼呈現（階段 4）。
