# 0020. CI 打包發佈、版本一致與 gitleaks 掃描

- 日期：2026-11-20
- 狀態：已採用

## 背景

5a、5b 的安裝檔都在作者的電腦上打包。5c 要讓 GitHub Actions 打包並上傳到 Release，CI 要掃完整歷史的密鑰，三處版本號要一致，App 的 exe 要有 Windows 版本資訊。
作者看過設計後 11 項全部照建議（2026-11-20）。

查證（2026-11-20，GitHub API 與官方文件）：

- Inno Setup 最新穩定版 7.1.1；`windows-latest`（Server 2025）與 `windows-2022` 預裝的是 6.7.1。issrc 的發佈附 x64 安裝檔，授權允許任何用途。
- Inno 的 `OutputManifestFile` 讓編譯器列出放進安裝檔的所有檔案。
- gitleaks 8.30.1（跟 pre-commit 同一版）。gitleaks-action 在 push 事件只掃這次推上來的 commit。
- runner 預裝 GitHub CLI，可以直接 `gh release create`。
- uv.lock 存 PEP 440 正規化過的版本（`1.0.0-rc.1` 寫成 `1.0.0rc1`）。

## 決定

1. **發佈的 workflow 是 `.github/workflows/release.yml`**，跟 `ci.yml` 分開。推 `v*` tag：`build` job 跑 `scripts/check.py`、打包、上傳 artifact，`release` job 建立 **draft** Release，作者核對後手動發佈。手動觸發（workflow_dispatch）只有 `build`。
2. **版本號帶 `-`（`1.0.0-rc.N`）的 Release 標成 pre-release**：`releases/latest` 不回它，App 不會把 rc 當成新版。
3. **權限**：預設 `contents: read`，只有 `release` job 是 `contents: write`。只用 `GITHUB_TOKEN`。checkout 一律 `persist-credentials: false`。
4. **上傳的只有兩個檔案**：`MediaDownloader-Setup-<版本>.exe` 與同名加 `.sha256`。`build_installer.py`（不加 `--test-update-source` 時）檢查 `packaging/output/` 只有這兩個、檔名符合格式、Inno 列出的檔案清單（`build/installer-manifest.txt`）裡沒有 `update-source-test`；`--release-tag` 要等於 `v<__version__>`，而且不能跟 `--test-update-source` 一起用。`release` job 再核對一次檔名與檢查碼。`test_update_source.py` 擋 workflow 出現 `test-update-source`。
5. **Inno Setup 7.1.1 在 runner 上自己裝**：從 jrsoftware/issrc 的發佈下載，核對寫死的 SHA-256，`/VERYSILENT /SUPPRESSMSGBOXES /NORESTART /CURRENTUSER`。不用預裝的 6.7.1，也不用 choco／winget。
6. **gitleaks 是 `ci.yml` 的一個 job**（ubuntu，`fetch-depth: 0`）：下載 8.30.1、核對寫死的 SHA-256，`gitleaks git --redact` 掃完整歷史。掃到東西 job 失敗，先停下來回報，不自己改寫歷史（計畫 1.2 第 10 項）。
7. **Actions 固定到 commit SHA**，版本寫在註解；`ci.yml` 一起改。
8. **artifact 保存 7 天。**
9. **版本一致**：`test_version.py` 比對 `__version__`、`pyproject.toml`、`uv.lock`（把 `-rc.N` 換成 `rcN` 再比），一般的 CI 就會跑；tag 由 `--release-tag` 比對。
10. **exe 的版本資訊**由 `packaging/media-downloader.spec` 從 `__version__` 產生：數字版本只有前三段加 0（`1.0.0-rc.2` 與 `1.0.0` 都是 `1.0.0.0`），檔案版本、產品版本的文字欄位放完整版本；產品名稱 Media Downloader；版權 `Copyright (c) 2026 kdwjzh`（跟 LICENSE 相同，沒有 email）。
11. **重試的錯誤維持一個集合**（`RETRYABLE` 含 `checksumMismatch`），改文件：`架構.md` 與約定 `retry_task` 原本寫「只有兩種」。

## 理由

- 1、2：draft 在發佈前可以先核對檔案與檢查碼；draft 與 pre-release 都不會被 `releases/latest` 回傳，裝了舊版的人不會誤更新。
- 4：檢查放在打包腳本裡，本機和 CI 跑的是同一段，本機就能驗；清單是安裝檔實際的內容，不用真的安裝。
- 5、6、7：版本與雜湊都寫死，跟本機用的是同一版，不信任套件庫或可以移動的標籤。這個 workflow 會產出給別人執行的安裝檔，又有寫入權限。
- 6：gitleaks-action 在 push 時只掃新的 commit，不符合「每次掃整個歷史」。`--redact` 讓掃到的值不會出現在記錄裡。
- 8：安裝檔約 110 MB，私人 repo 的儲存有額度；要再測可以重新觸發。
- 9：格式已經被 `test_the_version_is_semver` 限定，用一行正規表示式就能正規化，不需要 `packaging` 套件。
- 10：App 自己的檔案在安裝時一律 `ignoreversion`，沒有地方比較這個數字；安裝檔的 `VersionInfoVersion` 原本就這樣做。
- 11：App 更新失敗後的「重試」不看這個集合，`checksumMismatch` 也不會出現在下載任務上；改文件不改行為，也不用改測試。

## 考慮過的其他做法

- 推 tag 直接發佈：少按一次，但發佈前沒有機會核對。
- 用 runner 預裝的 Inno 6.7.1：`build_installer.py` 只找 Inno Setup 7，6 版也沒驗過我們的腳本。
- 在 runner 上真的安裝一次再找標記檔：沒有 WebView2 時，`/SUPPRESSMSGBOXES` 會採用「否」，安裝程式中止。
- 第四段放 rc 編號（`1.0.0.2`、正式版 `1.0.0.1000`）：要自己訂規則，沒有東西用得到。
- 把 `checksumMismatch` 從 `RETRYABLE` 拿掉：比較精確，但要改後端、`types.ts` 與測試，只是擋住一個不會發生的情況。

## 代價

- 升級 Actions、Inno、gitleaks 都要手動換 SHA 或雜湊（沒有 Dependabot）。
- 發佈要作者在 GitHub 上手動按「Publish」。
- 已知代價（5b 留下的）：打包後的 App 一開就在背景自動更新 yt-dlp（`0019`）；如果剛好有下載在這時啟動，可能碰到換檔的空檔，下載失敗（可以重試）。
- Inno 的檔案清單格式沒有文件，檢查只看標記檔的名字有沒有出現在清單裡。
- exe 的數字版本分不出 rc 和正式版，要看文字欄位。
