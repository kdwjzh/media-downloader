# 0006. 視覺方向「唱片封套」與主畫面的操作方式

- 日期：2026-11-13
- 狀態：已採用

## 背景

階段 2 要在寫功能之前定出畫面的樣子。開始時視覺方向還沒定，`docs/介面設計依據.md` 也留了一個問題：預覽還沒加入佇列時，使用者又貼了另一個網址要怎麼處理。

限制是：只有淺色模式但之後要能加深色、介面有繁體中文和英文、視窗預設 960x680、桌面程式要能離線開啟。

用 ui-ux-pro-max 產生的配色與字體候選都是這類產品的標準長相，而且各有問題：主色是紅色（跟失敗狀態衝突）、只支援深色、主按鈕只能放黑字；字體都沒有中文字，也都假設從網路載入。所以另外提了三個方向（調音台、唱片封套、Windows 內建工具）讓維護者選。

## 決定

1. **視覺方向用「唱片封套」**：淡紫白背景、梅紫主色、芥末黃只當 MP3 標籤的底色。完整的顏色、字體、元件規則在 `design-system/media-downloader/MASTER.md`。
2. **縮圖的形狀代表格式**：MP3 裁成正方形，MP4 維持 16:9。
3. **字體隨 App 附帶**：Noto Sans TC 與 Bricolage Grotesque（都是 OFL 1.1），不用系統字體，也不從網路載入。
4. **顏色一律用語意變數**，元件裡不寫色碼。
5. **導覽放左側**（下載、歷史紀錄、設定），視窗最小 720x520。
6. **預覽還沒加入時又貼了另一個網址**：舊預覽已查到的自動加入佇列；還在查詢中的也加入佇列，以「查詢資訊中」顯示；查詢失敗的直接換掉。
7. **清空歷史紀錄要先確認**；刪除單筆紀錄、從佇列移除項目不用確認。

## 理由

- 這個 App 以抓音樂為主，MP3 成品真的會把縮圖嵌成封面。正方形縮圖讓使用者不用讀字就分得出佇列裡哪些是音樂、哪些是影片，特色來自用途而不是裝飾。
- 主色選得夠深，白字放上去就及格（9.74:1），主色也能直接當文字用，比候選配色少很多限制。所有文字與背景的組合都算過對比並列在規範裡。
- 附帶字體讓每台電腦看起來一樣，代價是安裝檔多大約 5 MB；跟 FFmpeg 的大小相比可以接受。
- 語意變數讓之後加深色模式只要換一張表。
- 清單型的畫面高度比寬度珍貴，導覽放上方會少一列佇列。
- 主要用途是連續抓很多首歌、格式通常不變。自動加入讓連續貼上不必每次按一下；佇列裡每一項都能取消，誤加的代價很小。
- 清空紀錄不可逆，確認視窗比做「復原」簡單。更新通知不用彈窗（舊版的問題）跟這個確認視窗是兩回事。

## 考慮過的其他做法

- **調音台**（鋁灰加綠、一格一格的電平表進度條、全部用系統字體）：進度條很有記憶點，但同時三個下載時可能偏吵。
- **Windows 內建工具**（系統字體、中性灰）：風險最低，但沒有特色，也練不到 UI 設計。
- **貼新網址時取代舊預覽**：最簡單，但連續抓歌要每首按一次，忘了按就丟掉一首。
- **多張預覽並排**：最有彈性，但最複雜，預覽疊多了會把佇列擠出畫面。
- **用系統字體**（微軟正黑體）：不增加安裝檔大小，但不同版本的 Windows 看起來不一樣。

## 後果

- 連續貼網址時，查詢失敗的錯誤會出現在佇列裡。這是「查詢失敗不進佇列」的唯一例外，已寫進 `docs/介面設計依據.md` 第 0 節。
- 關於頁與 README 的授權清單要多列兩個字體。
- 芥末黃和分隔線色的對比不夠當文字或控制項邊框，規範裡明文限制了用途。
- 視窗在 720x520 且預覽開著時，佇列只看得到一列半。階段 4 實作時再決定要不要提高最小高度。
- 後端的錯誤代碼（階段 3）要跟規範第 8 節的 `error.*` 鍵名對齊。
