# 0021. 公開前的文件語言、第三方授權與個人資料搜尋

- 日期：2026-11-20
- 狀態：已採用

## 背景

5d 要在 repo 公開前把文件準備好（`docs/階段5-計畫.md` 的 5d）。
翻譯範圍作者在 2026-11-18 決定過：只翻 README.md、CHANGELOG、CLAUDE.md。這次要決定的是第三方授權怎麼列、CHANGELOG 怎麼寫、兩份 README 的關係，以及個人資料搜尋找到的東西怎麼處理。

查證（2026-11-20）：

- 個人資料搜尋：完整歷史 76 個 commit，作者與提交者都是 noreply 信箱；沒有找到 email、個人路徑、舊專案網址、不該進 git 的檔案；`brand/concepts/` 都是自己做的。找到但決定保留的見決定第 6 項。

## 決定

1. **文件語言**：README.md、CHANGELOG.md、CLAUDE.md 是英文；README.zh-TW.md、`docs/`、`design-system/` 維持中文，兩份 README 都註明。
2. **兩份 README 一段對一段**，內容相同，開頭互相連結；改一份就改另一份。
3. **README 的第三方元件表列 7 個**：yt-dlp、FFmpeg（原始碼連結指到實際附帶的那個建置）、Deno、兩個字體、pywebview、truststore；其他套件一句話指向安裝資料夾的 `licenses`。
4. **授權全文由打包自動產生**：`build_installer.py` 把後端執行時需要的 Python 套件（從 `pyproject.toml` 的 dependencies 往下找，以 `backend/.venv` 裡裝的為準）的授權檔與 Python 本身的授權合成 `ThirdParty-Python.txt`，Vite 產生的 npm 清單存成 `ThirdParty-Frontend.md`，安裝程式放進 `{app}\licenses`。缺授權檔的套件讓打包失敗；本身沒附的（proxy-tools）與 WebView2 SDK 的授權手動放在 `packaging/licenses/`。
5. **關於頁**：表格維持 5 個元件，下面加一句「所有授權全文在安裝資料夾的 licenses」。
6. **CHANGELOG** 的 `[Unreleased]` 整理成使用者看得懂的第一版內容（依功能分組），不留開發過程（樣張、還沒接上介面這類）；那些在 git 歷史與 `docs/`。標題留給 5e 改成 `[1.0.0]`。
7. **個人資料搜尋找到的**：
   - `階段5-計畫.md` 提到規劃工具（對話服務）的兩句改掉；commit `d73bde3` 的訊息不改。
   - commit 的 `Co-Authored-By: Claude` 保留。
   - `ui-ux-pro-max`、`frontend-design`、`logo-design` 是用過的工具名稱，保留。
   - 「作者的電腦連手機熱點」這類描述、測試樣本裡別人的公開播放列表，保留。
   - 歷史不改寫，也不開新 repo。
8. **`.sha256` 用 LF 換行**：舊版 GNU `sha256sum -c`（coreutils 9.0 以前）遇到 CRLF 會找不到檔案。

## 理由

- README 只列主要的元件好讀，完整清單由打包產生，套件升級時不會跟實際附帶的不一致；MIT、BSD 要求散布時附上授權文字（非法律意見）。
- 關於頁要列全部就得在打包時帶套件的中繼資料才讀得到版本，而且還是列不全；一句話指向資料夾就夠了。
- 第一個公開版本的 CHANGELOG 是給使用者看的，Release 說明也從這裡取。
- 找到的都不是個人資料；改寫歷史要強制推送，代價大於好處。
- 用 Git Bash 的 coreutils 8.32 實測：LF 是 `OK`，CRLF 是 `FAILED open or read`。

## 考慮過的其他做法

- README 列全部約 20 個套件：每次升級都要改兩份。
- 手寫一份第三方授權檔：套件升版後會過時。
- 用 `pip-licenses` 一類的套件產生：要多一個依賴，標準函式庫的 `importlib.metadata` 就做得到。
- 英文 README 精簡：兩份不一致就要記得哪裡不同，維護比較麻煩。
