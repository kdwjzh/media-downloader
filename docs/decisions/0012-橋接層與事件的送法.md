# 0012. 橋接層與事件的送法

- 日期：2026-11-16
- 狀態：已採用

## 背景

階段 4a 要把階段 3 的後端接到網頁：指令從網頁進來，事件從後端出去。
事件來自三種執行緒（佇列的送事件執行緒、下載的執行緒、拿著設定寫入鎖的指令執行緒），
送進網頁要等介面那條執行緒，視窗還沒準備好或正在關閉時會失敗（`階段4-交接.md` 3.3）。
作者也決定關閉視窗時，還有任務沒結束就先問（`階段4-計畫.md` 第 1 節第 2 項）。

以下 pywebview 的行為是讀 6.2.1 的原始碼確認的（`.venv` 裡的 `webview/`），並對過官方 API 文件：

- `js_api` 物件上名字不是底線開頭的屬性都會公開給網頁，連屬性的屬性也會。
- 網頁每次呼叫指令，pywebview 開一條新的執行緒；指令丟出的例外會變成網頁那邊一段英文錯誤。
- `evaluate_js` 會先等頁面準備好（最多 20 秒，等不到丟例外），再等介面執行緒跑完腳本。
- `window.events.closing` 的處理函式在介面執行緒上同步執行，回 `False` 就取消關閉。
  它裡面不能呼叫 `evaluate_js`：那要等同一條介面執行緒，會死結。
- 資料夾對話框是 `window.create_file_dialog(FileDialog.FOLDER, directory=…)`，回傳 tuple，按取消是 `None`。

## 決定

1. **事件**：網頁的 `api/` 在 `window` 掛一個函式 `mediaDownloaderEvent`。後端的 `emit` 只把事件放進 `queue.SimpleQueue` 就返回；
   一條 daemon 執行緒取出、轉成 JSON、用 `evaluate_js` 呼叫它。腳本先檢查函式在不在，回傳網頁有沒有收到。
2. **收不到的事件丟掉**，不重送：頁面還沒掛上函式（載入中、開發時重新整理）、送失敗、或已經在關閉。介面啟動時本來就會拿完整的佇列與設定。
3. **關閉前確認**做在網頁裡：多一個事件 `closeRequested` 和一個指令 `confirm_close`（約定變成 25 個指令、6 種事件）。
   - 有任務不是 `done`、`failed`、`cancelled` 時，`closing` 的處理函式送 `closeRequested` 並回 `False`；沒有就直接關。
   - 網頁確認後叫 `confirm_close`，後端記住「確定要關」再關視窗，這次 `closing` 放行。
   - `closeRequested` 送不進網頁時，後端自己直接關，視窗不會關不掉。
   - `api/` 裡沒有人訂閱 `closeRequested` 時直接叫 `confirm_close`，所以 4b 做確認畫面之前，行為是照常關閉。
   - 「還有沒有任務」由橋接層對照 `domain/task.py` 的 `FINISHED` 判斷，服務層不用改。
4. **橋接層不碰 pywebview**：`main.py` 把「在網頁執行腳本」「開資料夾對話框」「關視窗」包成函式交給它。橋接層只 import 服務與領域層。
5. **每個指令都包起來**：`EngineError` 回它的代碼，其他任何例外回 `unknown` 並寫進記錄檔。`api/` 的函式也永遠回 `{ok, …}`，不會丟出去。
6. **資料形狀的轉換**集中在 `bridge/shapes.py`：小駝峰、`None` 的欄位拿掉、tuple 轉清單、佇列項目的進度攤平、`skipped` 只在是真的時出現、`speedBps` 四捨五入成整數。
7. **兩邊一致靠測試**：`test_bridge_*.py` 把約定第 2–4 節的 JSON 逐欄手寫出來比對；`test_types_ts.py` 讀 `types.ts` 與 `api/index.ts`，
   比對每個型別的欄位名稱與可不可以沒有、事件的種類、指令名稱、接收函式的名稱。只改一邊就會失敗。
8. **選到不能寫入的資料夾**回 `unknown`，介面對這個指令的失敗一律顯示專屬文案；不另加錯誤代碼。
9. **啟動**：`build()` → `backend.start()` → 建視窗、掛 `closing` → `webview.start(events.start)`。結束時先停止送事件，再 `backend.shutdown()`。
   `build()` 失敗時跳 Windows 的訊息框（中英文各一句加例外的類型與內容）後結束；這是後端唯一自己顯示的文字。
   外部程式不見時不另外檢查，照常啟動，用到時指令回 `unknown`。

## 理由

- 自己排隊再送：`emit` 被卡住的話，設定的寫入鎖、下載的空位、佇列的事件都會跟著卡住。單一執行緒送也讓三個來源的事件在網頁照同一個順序到。
- 不重送：補送的事件可能已經過期（例如舊的百分比），介面靠啟動時拿的完整狀態就對得上。
- 關閉確認在網頁裡：文字照「後端不回傳給人看的文字」的規則放在語言檔，樣子照設計規範。原生訊息框做不到這兩件。
- 不加 `folderNotWritable`：要改 domain、`types.ts`、兩份語言檔、約定、設計規範與所有寫「12 個」的地方，換來的只是一個指令的文案。

## 代價

- 開發時整頁重新整理的瞬間可能漏掉一筆事件，下一筆 `tasksChanged` 會補正。
- `choose_download_folder` 如果因為別的 bug 失敗，畫面也會說「無法寫入」；原因在記錄檔。
- `confirm_close` 的回覆可能來不及送到網頁（視窗已經關了），網頁不能等它。
- 啟動失敗的訊息框文字寫死在 `main.py`，不跟著介面語言。

## 沒採用的做法

- 介面定時來問事件（輪詢）：要多一個指令，而且進度會延遲。
- 後端跳原生的關閉確認視窗：不用改約定，但文字在後端、樣子不照設計規範。
- 頁面還沒準備好時把事件留著等它出現再補送：要處理補送過期事件的問題，換來的是啟動時本來就會拿到的狀態。
