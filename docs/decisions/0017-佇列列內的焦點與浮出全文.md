# 0017. 佇列列內的焦點、按住不放的按鍵、被截斷文字的浮出區塊

- 日期：2026-11-18
- 狀態：已採用

## 背景

階段 4f 收尾時處理了 4e 留下的兩個問題與交接第 17 項：

- 佇列的列依狀態整組換按鈕（取消 → 重新加入、✕），焦點可能掉到頁面上。
- 按住 Enter 或空白鍵時，重複的按鍵會一直觸發會來回切換的動作。
- 最小視窗（網頁 707 寬）的英文介面，有些失敗的列錯誤訊息被截斷；滑鼠停上去看得到 `title`，只用鍵盤的人看不到下一步。

作者驗收時又發現浮出區塊的三個問題（重複顯示看得到的錯誤、被清單切掉、按鈕換了之後蓋住新按鈕），都在這份決定裡一起處理。

## 決定

1. **焦點留在同一列**：焦點在某一列的按鈕上、那一列換了狀態（自己按的取消、重試、重新加入，或下載自己結束），焦點留在同一列的第一顆按鈕。做法是第一顆按鈕在每個狀態都用同一個 `key`，React 沿用同一個元素。
2. **按 ✕ 移除後焦點維持移到「佇列（N）」標題**（作者決定，沒改成移到相鄰的列）。「清除已結束的」「取消全部」同樣維持。
3. **按住不放只認第一下**：佇列列內的按鈕（Enter）、播放列表清單（空白鍵）忽略重複的按鍵；按住方向鍵照常移動。
4. **焦點時浮出被截斷的全文**（作者選 B）：焦點在列內的按鈕上時，被截斷的部分浮在文字欄上方。只放被截斷的部分（只有標題被截斷就只放標題）。焦點在文字欄裡的「開啟記錄檔」上時不浮出，否則會蓋住它。
5. **浮出區塊用 `position: fixed`**，不在清單的捲動範圍裡，比那一列高時也不會被切掉；清單捲動或視窗改變大小時收起。顯示的期間，每次重畫都重新量位置與被截斷的部分。

## 理由

- 1：靠 React 剛好沿用元素不可靠（4f 寫測試時發現，「失敗而且不能重試」那種就會掉）；固定 `key` 讓它一定成立，也比另外記住焦點、事件來了再移動的寫法少。焦點留在原地，朗讀程式會唸出新的按鈕名稱（作者驗收時確認）。
- 2：作者的決定。
- 3：焦點留在同一個元素上，而它變成相反的動作，按住 Enter 會「取消 → 重新加入 → 取消」來回切換。跟 4e 歷史刪除的做法相同。
- 4：只放被截斷的部分，區塊才不會比需要的高；重複顯示看得到的錯誤會讓區塊超出那一列（作者驗收時發現）。
- 5：清單本身會捲動，`absolute` 的區塊超出那一列的部分會被切掉、清單還多出捲軸。`fixed` 跟不上捲動，所以捲動時收起。按鈕換了之後文字欄的寬度會變，只在拿到焦點時量一次會蓋住新按鈕（作者驗收時發現）。

## 考慮過的其他做法

- 按 ✕ 後焦點移到接替位置那一列（比照歷史的刪除）：作者決定維持移到標題。
- 錯誤被截斷時維持現狀（只有滑鼠看得到全文）、或把英文提示再縮短：前者鍵盤使用者讀不到下一步；後者以後新的文案還是可能被截斷。
- 標題和錯誤都被截斷時，區塊裡的標題只顯示一行讓位置給錯誤：程式最少，但標題又看不全。
- 區塊放在清單裡、往上長或往下長：清單只有一列時兩個方向都會被切掉。

## 代價

- 浮出區塊可能暫時蓋住下面那一列，或文字欄裡的「開啟記錄檔」（Tab 移到連結時就收起）。
- 捲動清單時區塊會收起，要再 Tab 一次才會出現。
- 列的祖先元素不能加 `transform`，否則 `fixed` 會被限制在它裡面。
- 「標題和錯誤都被截斷」只在真視窗用假資料量過（很難做出真的未知錯誤）。
- 失敗訊息換到第二行時從圖示底下開始，不跟第一行的文字對齊（圖示放進文字裡才能跟第一行對齊）。
