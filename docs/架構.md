# Media Downloader 架構

> 狀態：已確認（決策點 A、B、實作順序皆定案）
> 版本：1.0（2026-11-11）
> 功能範圍見 `功能規格.md`；決策紀錄見 `decisions/`；決定與規則見根目錄 `CLAUDE.md`（與本文件衝突時以 `CLAUDE.md` 為準）

---

## 摘要

- **組合**：pywebview（桌面視窗）+ React / TypeScript / Tailwind（介面）+ Python（後端）+ yt-dlp 官方執行檔（下載引擎）。
- **分五層**：介面 → 橋接 → 服務 → 領域模型 → 基礎設施。上層只能呼叫下層，下層用事件通知上層。
- **多平台**：下載引擎定義統一介面，yt-dlp 是第一個實作，Telegram 之後可以是第二個。
- **實作順序**：骨架 → 技術驗證 → UI 設計 → 後端 → 介面 → 打包。

## 1. 決策 A：桌面外殼用 pywebview

| | pywebview（採用） | Tauri + Python sidecar |
|---|---|---|
| 語言數量 | 2（Python、TypeScript） | 3（多一個 Rust） |
| 前後端溝通 | JS 直接呼叫 Python 函式 | 介面 → Rust → 另一個 Python 程序，要自己定通訊格式 |
| 打包 | PyInstaller + 安裝檔製作工具（如 Inno Setup） | 內建安裝檔製作 |
| App 自動更新 | 自己寫（下載新版安裝檔並執行） | 有官方 updater 外掛，需設定簽章金鑰 |
| 除錯難度 | 一個程序，問題好找 | 三段式，出錯時要判斷是哪一段 |
| 已知風險 | 功能較陽春，視窗細節（自訂標題列等）彈性較小 | 有回報指出 PyInstaller 做的 sidecar 在重新安裝時可能沒被換掉 |

理由：可維護性優先。介面層只透過橋接層跟後端講話，日後想換成 Tauri，要改的只有橋接層。

## 2. 決策 B：呼叫 yt-dlp 官方執行檔

背景：yt-dlp 從 2025.11.12 版起，YouTube 下載需要外部 JavaScript 執行環境（建議 Deno）和 yt-dlp-ejs 元件；官方執行檔已內含 yt-dlp-ejs。這是舊版沒有的新依賴。

| | 當 Python 函式庫打包 | 呼叫官方 `yt-dlp.exe`（採用） |
|---|---|---|
| yt-dlp 更新 | 要重新打包、發新版 App | 執行 `yt-dlp -U` 即可，跟 App 版本無關 |
| 取消下載 | 要在回呼裡丟例外中斷，暫存檔要自己清 | 結束該程序樹，再刪掉該任務的暫存資料夾 |
| 當掉的影響 | 可能拖垮整個 App | 只影響那一個下載 |
| 進度資訊 | 直接拿到 Python 字典 | 用進度樣板輸出 JSON 再解析 |
| ejs 元件 | 要自己確保版本對得上 | 官方執行檔已內含 |

隨 App 附帶的外部程式：`yt-dlp.exe`、`ffmpeg.exe`、`deno.exe`（不附 `ffprobe.exe`，實測用不到）。三個執行檔共 278.4 MiB，壓縮後約 97.9 MiB；較小的 FFmpeg 建置留到打包階段評估。

**外部程式的存放位置**：yt-dlp 要能自我更新，所在資料夾必須讓一般使用者可寫入，`C:\Program Files` 不行。安裝檔採「僅目前使用者」安裝（裝到 `%LOCALAPPDATA%\Programs`），外部程式跟 App 放在同一個安裝資料夾。見 `decisions/0005`。

### 規則

| 規則 | 目的 |
|---|---|
| 上層可以呼叫下層，下層不能 import 上層 | 改介面不會動到下載邏輯 |
| 下層要通知上層時只發事件 | 解決舊版 C2（背景執行緒直接改 UI） |
| 只有 `infrastructure/engines/ytdlp/` 知道 yt-dlp 的存在 | 換引擎或加引擎時，其他層不用改 |
| 後端回傳錯誤代碼，不回傳文字 | 文字由介面層依語言翻譯，中英雙語才好維護 |
| 外部程式只能透過 `binaries/` 取得路徑 | 開發環境與打包後的路徑差異集中在一處 |
| 每個下載任務的狀態只能由 `DownloadTask` 的狀態機改變 | 避免舊版那種到處改旗標的情況 |
| 介面只有 `frontend/src/api/` 能呼叫橋接層 | 換外殼或改通訊方式時只動一個資料夾 |

### 任務狀態

九種狀態，後端與介面用同一組字串（2026-11-14 改成階段 2 定案的名稱）：

```
fetching ──→ queued ──→ downloading ⇄ retrying
                              │
                              ├──→ converting ──┐
                              ├──→ merging ─────┼──→ done
                              └─────────────────┘
retrying ──→ done（引擎回報成功時，不管當下是哪個下載中的狀態都算完成）

done 以外的每個狀態 ──→ cancelled ──→ queued / fetching（重新加入）
fetching、downloading、retrying、converting、merging ──→ failed ──→ queued / fetching（重試）
```

- `fetching` 只代表「還不知道影片資訊，正在查」；只有「只給網址」加入的任務會經過它。
- `converting` 只有 MP3、`merging` 只有 MP4。檔案已存在而略過是 `downloading → done`：檔名要等下載開始才知道，所以沒有 `queued → done`。
- 重試只適用於 `network` 與 `unknown` 兩種錯誤。
- 完整的轉換表在 `介面與後端的約定.md` 第 6 節，實作在 `backend/app/domain/task.py`。

進度由領域層把每個檔的位元組合成一條總進度（解決 U3）：MP4 的影像與聲音只從 0 跑到 100 一次，百分比只增不減；算法見約定 2.7。只有下載階段有百分比；查資訊與後處理（轉檔、合併、嵌入封面）只有開始與結束，介面顯示階段名稱與不確定進度。

### 佇列（`services/queue.py`）

決定的理由在 `decisions/0010`。

- 任務只能在拿著 `QueueService` 的鎖時被改。每個下載一條執行緒；只有網址的任務另外用 2 條執行緒查資訊，不佔同時下載數。
- 空位以還活著的下載執行緒計算：被取消的任務要等引擎收尾完才讓出空位，同一個任務也要等舊的一輪結束才會再開始。
- 每個任務每次開始查詢或下載換一個輪次編號，舊輪次的事件與結果不採用。
- 事件在鎖裡排進佇列，由另一條執行緒照順序交給介面；內容是當下的快照 `QueueItem`（沒有成品路徑）。佇列只送 `tasksChanged`、`tasksRemoved`、`taskProgress`。
- 進度節流：距離上次不到 0.5 秒或數字沒變就丟掉，不留著補送。
- 下載資料夾在加入時決定；檔名重複的規則在開始下載時讀設定。
- 引擎丟出的任何例外都會讓任務結束：`EngineError` 照代碼失敗，其他一律 `unknown`，原文用 `logging` 記下來。
- 佇列需要的設定與歷史定義在 `services/ports.py`（`QueueSettings`、`HistoryRecorder`），由 `SettingsService` 與 `HistoryService` 實作；測試用的記憶體版在 `tests/fakes.py`。
- `MediaInfoService`（`services/media_info.py`）：整理使用者貼的文字、記住查過的標題與縮圖（上限 5,000 筆）、同一個網址正在查時共用結果。
- 啟動時 `start()` 清掉設定列出的資料夾裡的暫存；關閉時 `shutdown()` 先擋住新的工作，再叫引擎全部停止，最多等 5 秒讓暫存資料夾刪完。

### 設定、歷史、更新、開啟外部的東西

決定的理由在 `decisions/0011`。

- 服務層不直接碰檔案格式、網路與 Windows：它們需要的東西定義成 `services/ports.py` 的介面，真的實作在 `infrastructure/`，由 `backend/app/composition.py` 的 `build()` 接起來。橋接層與 `scripts/manual/` 都從 `build()` 開始。
- `SettingsService`（`services/settings.py`）：設定是一個不可變的物件，讀取不拿鎖；修改拿寫入鎖，存檔與 `settingsChanged` 都在鎖裡。驗證規則在 `domain/settings.py`。
- `HistoryService`（`services/history.py`）：每筆有自己的編號；縮圖存在資料庫裡；成品路徑與原始縮圖網址只留在後端。「重新下載」經由組裝處給的函式加入佇列。
- `UpdateService`（`services/updates.py`）：App 新版檢查（結果存 24 小時，查不到存 1 小時）、更新引擎、關於頁的資料。
- `ExternalService`（`services/external.py`）：開啟資料夾並選中檔案、開啟記錄檔與它的資料夾、開啟兩個固定的網頁。
- `infrastructure/http.py` 是 App 自己連網路的唯一入口（https、主機允許清單、不跟隨轉址、大小上限）。
- `infrastructure/process.py` 是啟動外部程式的唯一入口（Job Object、不出現主控台視窗）。
- 資料位置：設定與歷史在 `%APPDATA%\media-downloader`，記錄檔與新版檢查的結果在 `%LOCALAPPDATA%\media-downloader`；開發時資料夾名稱多 `-dev`。

### 橋接層（`bridge/`）

決定的理由在 `decisions/0012`。

- `bridge/api.py` 的 `BridgeApi`：約定的 25 個指令，每個都回 `{ok, data}` 或 `{ok, error}`，任何例外都不漏給網頁。pywebview 會公開它所有不是底線開頭的屬性，其他成員一律底線開頭。
- `bridge/shapes.py`：服務的資料類別轉成約定的 JSON（小駝峰、沒有值的欄位不出現、進度攤平、事件加 `type`）。
- `bridge/events.py` 的 `EventSender`：`emit` 只排隊；一條執行緒依序轉成 JSON 送進網頁的 `window.mediaDownloaderEvent`。排在一起的 `tasksChanged` 合成一個送（同一個任務只留最新的，位置照第一次出現的；中間夾著別種事件就不合，見 `decisions/0014`）。收不到就丟掉；`closeRequested` 收不到時直接關視窗。
- 橋接層不碰 pywebview，也不 import `infrastructure/`：`main.py` 建好服務（`composition.build()`）、視窗，把「執行腳本」「開資料夾對話框」「關視窗」包成函式交給它。
- 關閉：有任務沒結束時 `closing` 回 `False` 並送 `closeRequested`；網頁確認後叫 `confirm_close`。
- 介面這邊只有 `frontend/src/api/` 碰 pywebview：`bridge.ts` 負責呼叫與接收，`index.ts` 每個指令一個函式、`onEvent`、`onCloseRequested`。不在 pywebview 裡時每個指令回 `{ok: false, error: 'unknown'}`。

## 4. 多平台預留

```python
class MediaEngine(Protocol):
    def fetch_info(self, url: str) -> MediaInfo | PlaylistInfo: ...
    def download(
        self, request: DownloadRequest, on_event: Callable[[EngineEvent], None]
    ) -> DownloadResult: ...
    def cancel(self, task_id: str) -> None: ...
    def stop_all(self) -> None: ...
    def remove_stale_temp(self, dest_dir: str) -> None: ...
    def version(self) -> str: ...
    def update(self) -> bool: ...
```

- 定義在 `backend/app/domain/engine.py`。
- 引擎拿到的是 `DownloadRequest`（編號、網址、格式、音質／畫質、下載資料夾、檔名重複時的處理），不是 `DownloadTask`：任務的狀態只能由狀態機改，引擎只回報事件，由服務層套用到任務上。
- `DownloadResult` 帶成品路徑、大小、是否略過。檔名重複的三種處理由引擎做：下載在任務自己的暫存資料夾完成，最後才搬進下載資料夾（`decisions/0009`）。
- `stop_all()` 是關閉 App 時全部停止；`remove_stale_temp(下載資料夾)` 是啟動時清掉上次留下的暫存資料夾，只能在沒有任務往那個資料夾下載時呼叫。
- 每個任務的程序都放在自己的 Windows Job Object 裡：取消是結束整個 Job，App 被強制結束時也會一起結束（`decisions/0008`）。
- 事件有四種：`FileSizes`（各個檔的大小）、`FileProgress`（某個檔下載到哪）、`ConnectionLost`（自動重試中）、`PostProcessing`（開始轉檔或合併）。
- 失敗丟 `EngineError`（帶 `ErrorCode`），被取消丟 `DownloadCancelled`。
- 沒有 `can_handle`：第一版只有一個引擎。引擎自己先用網域清單擋掉不是 YouTube 的網址（`youtube.com` 與子網域、`youtu.be`、`youtube-nocookie.com`），通過的才交給 yt-dlp 判斷是哪一種網址（C9）。加第二個引擎時再加 `can_handle`。

| 階段 | 引擎 | 涵蓋 |
|---|---|---|
| 第一版 | `YtDlpEngine` | YouTube（只測試並保證這個） |
| 之後 | `YtDlpEngine`（同一個） | TikTok、Instagram、X 等；主要補 cookies 登入與介面調整 |
| 之後 | `TelegramEngine`（新增） | Telegram，需帳號登入，獨立評估 |

`MediaInfo` 帶 `platform` 欄位，介面據此顯示平台標示。

## 8. 實作順序（折衷方案，已確認）
